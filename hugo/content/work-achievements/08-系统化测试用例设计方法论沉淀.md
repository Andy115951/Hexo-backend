## 一句话成就

把测试设计从"凭经验、靠感觉、随缘覆盖"升级为系统化双阶段流程（建模 → 表格化），先系统性暴露风险，再按优先级产出可执行的测试用例，形成风险驱动的可复用测试设计方法论。

---

## 成就卡片

- 成就编号：A08
- 时间范围：2026-04 ~ 2026-05
- 业务域：测试方法论 / 测试设计 / 质量工程
- 你的角色：方法设计 + 工具链建设 owner
- 影响对象：测试设计质量、用例评审效率、新人上岗速度
- 产出类型：方法论文档 / 模板 / CLI 集成（AI Skill）

---

## 背景与问题定义

### 1) 业务场景

产品功能迭代快、业务逻辑日益复杂（多角色协作、状态机流转、并发竞态、局部失败等），测试设计面临的核心挑战不再是"会不会写用例"，而是"设计是否完整、风险是否被覆盖"。

### 2) 原始痛点

1. **用例设计依赖个人经验**：同一功能不同人设计的用例质量差异大，重要边界和风险场景容易被遗漏。
2. **评审靠感觉**：评审时只能凭经验判断"够不够"，缺少结构化的检查清单和覆盖标准。
3. **自动化与手工脱节**：手工用例和自动化用例两套体系，测试设计的结果难以平滑过渡到自动化执行。
4. **复盘缺乏依据**：线上故障回溯时，难判断是测试设计遗漏还是执行不到位。
5. **新人上手慢**：测试设计方法论停留在口头传帮带，没有可查阅、可执行的标准流程。

### 3) 影响评估

- **质量风险**：核心边界和竞态场景遗漏，导致线上漏测
- **效率成本**：用例评审和返工占设计总时间的 40%+
- **资产损失**：测试设计经验随人员流动流失，无法复用

---

## 目标与验收标准

### 1) 目标

1. 建立可复用的系统化测试设计方法论，覆盖从需求理解到用例输出的完整链路。
2. 以"风险驱动"替代"功能点覆盖"作为设计核心原则。
3. 输出物结构清晰，可评审、可追溯、可直接为自动化提供输入。
4. 方法论本身可持续演进，新模块可直接套用。

### 2) 验收标准

- 方法论包含明确的两阶段划分：建模阶段（不写用例）→ 表格化阶段（转用例）。
- 建模阶段覆盖至少 10 个分析维度（流程、数据、状态机、并发、局部失败、权限等）。
- 表格化阶段按优先级分层（P0/P1/P2），每级有明确的门禁定义。
- 输出为标准化 .md 文档，评审方无需额外解释即可理解。
- 可通过 AI Skill 形式嵌入工具链，降低使用门槛。

---

## 约束与边界

- 约束 1：方法论必须兼容手工测试和自动化测试两种场景，不偏向任何一端。
- 约束 2：输出物必须是纯文档（.md），不依赖特定测试框架或平台。
- 约束 3：方法复杂度的上限是要让新人能在 1-2 次实践后独立使用。
- 非目标：本阶段不实现自动化生成用例代码，只做设计层面的标准化。

---

## 核心原理（为什么这样设计）

1. **先暴露风险，再决定测什么**
   很多人上来就写用例——这是错的。应该先系统性分析"哪里可能出问题"，再按风险和成本决定覆盖优先级。不分析直接写，漏的一定比想到的多。

2. **建模和用例生成必须解耦**
   建模关注的是"系统应该怎么工作、哪里会出问题"，用例关注的是"具体怎么验证"。混在一起会导致：要么用例质量被建模质量拖累，要么建模不完整但用例看起来很多。

3. **用例必须有优先级分层**
   资源永远有限。P0（发布阻断）、P1（主要回归）、P2（边界/低频）的分层让执行决策有依据，而不是每次靠"赌"。

4. **测试设计也是工程资产**
   系统化的设计文档可评审、可审计、可复用、可传承。当测试设计从"个人脑中的经验"变成"可读的文档"，团队的测试能力就不再依赖于特定个人。

### 原理流转图

```text
需求/PRD 进入测试池
  -> 建模阶段（不写用例）
    -> 1. 范围定义（In/Out of scope）
    -> 2. 流程逻辑（多角色视角 + 交汇点）
    -> 3. 数据模型（实体/约束/一致性/补偿）
    -> 4. 状态机（合法 + 非法流转）
    -> 5. 并发与竞态（重复/重试/交叉）
    -> 6. 权限与安全隔离
    -> 7. 测试矩阵（高风险组合）
    -> 8. 风险识别与裁剪建议
  -> 表格化阶段
    -> P0 用例（发布阻断：Happy Path + 权限 + 幂等）
    -> P1 用例（主要异常 + 状态变更 + 边界）
    -> P2 用例（低频风险 + 兼容性 + 性能）
    -> 风险补充 + 覆盖映射 + 门禁定义
  -> 输出标准化 .md 文档
    -> 可评审 / 可追溯 / 可对接自动化
```

## 我的关键动作

### 1) 方法论设计阶段

- **分析市面上测试设计方法的不足**：传统等价类/边界值覆盖了"输入"，但覆盖不了"状态、并发、局部失败"；基于场景的方法覆盖了"流程"，但覆盖不了"数据一致性和权限"。
- **设计双阶段流程**：把"分析"和"编写"解耦成两个独立阶段，每个阶段有明确的检查清单和产出标准，避免混在一起时顾此失彼。
- **定义 8 大建模维度**：从多次线上故障和测试漏测中归纳出反复出问题的维度——流程、数据、状态、并发、权限、失败补偿、环境、风险裁剪。

### 2) 模板化与标准化阶段

- **为每个建模维度设计标准表格模板**：例如测试矩阵模板（维度×取值+高风险组合）、Partial Failure 模型模板（已成功步骤/失败步骤/补偿逻辑）、状态机模板（合法/非法流转+并发竞态表）。
- **定义 P0/P1/P2 优先级门禁**：明确哪类用例必须 P0（核心流程、权限、幂等、数据完整性），哪类可以放 P1/P2。
- **设计覆盖映射机制**：每个用例在表格中标明类型（Happy Path / Error / State / Concurrency 等），最后汇总覆盖矩阵，确保无维度遗漏。

### 3) 工具链集成阶段

- **将方法论封装为 AI Skill 文件**：`test-case-step1-markdown`（建模）和 `test-case-step2-table`（表格化），使 AI 工具能按此方法论引导使用者完成完整的测试设计流程。
- **设计步骤间的前置依赖**：step1 未完成不允许进入 step2，确保方法论不会被跳过或打乱。
- **集成到项目级 .claude/skills 目录**：通过符号链接在 autotest2py 项目中可用，输出文档统一存入 `tests/test-case-docs/` 目录。

### 4) 验证与迭代阶段

- **在 chatbox-session-attachment-rag 功能上试跑全流程**：从建模到表格化，验证方法论在真实功能上的可操作性。
- **在 chatbox-invitation 功能上再次验证**：确认方法论对不同类型功能的通用性。
- **根据实践反馈调整模板细节**：简化过于复杂的表格结构，增加风险裁剪建议的参考标准。

---

## 难点、风险与应对

### 1) 难点

- **方法论的复杂度与易用性平衡**：建模维度过少会漏风险，维度过多新人望而却步。需要在"完整"和"可用"之间找平衡点。
- **从"习惯写用例"到"先建模再写用例"的行为转变**：大部分人习惯直接上手写用例，建模阶段感觉"在浪费时间"。

### 2) 风险与应对

- **风险**：方法论沦为文档模板，实际使用时不走心、走过场。  
  **应对**：用外部检查清单（完成 checklist）和步骤间强制依赖（step1 未完成不能进 step2）来约束使用流程。
- **风险**：不同模块的设计深度不一致，质量参差。  
  **应对**：标准化模板自带"必须覆盖"的基线要求，降低个体差异带来的质量波动。

### 3) 关键突破

- **从"用例数量"到"风险覆盖"的思维转变**：方法论的核心不再是"写了多少条用例"，而是"哪些风险被识别了、哪些被覆盖了、哪些决定不覆盖"。
- **AI Skill 化降低了方法论的传播成本**：不需要培训宣讲，AI 会在使用过程中引导使用者一步步完成流程。

## 结果与影响

### 1) 短期结果

1. 形成了完整的双阶段测试设计方法论文档和模板。
2. 产出两个 AI Skill 文件（step1-markdown + step2-table），可直接在 Claude 中调用。
3. 在两个真实功能上验证了方法论的可行性和通用性。

### 2) 中期价值

1. 测试设计的质量从"依赖个人经验"变为"依赖系统化流程"，新人产出质量下限显著提高。
2. 用例评审从"感觉够不够"变为"对照检查清单逐项确认"。
3. 测试设计文档成为可审计、可追溯的工程资产，而非一次性产物。

### 3) 长期复用价值

1. 方法论可迁移到任何业务域或技术栈——不绑定测试框架、编程语言或平台。
2. 建模阶段的"风险识别"思维可以反向影响需求评审和架构设计，提升整个团队的质量意识。
3. AI Skill 化的方式可作为模板：类似的知识体系（如代码评审 checklist、安全审计流程）都可以用同样的方式沉淀为可调用技能。

## 关键代码与命令片段

### 1) 建模阶段检查清单（模板示例）

```text
建模阶段必须覆盖的维度：
□ 范围定义（In/Out of scope）
□ 流程逻辑（所有角色视角 + 交汇点）
□ 数据模型（实体、约束、不变量）
□ 测试矩阵（维度 + 高风险组合）
□ 数据一致性与补偿模型
□ 权限、安全与隔离模型
□ 状态机（合法 + 非法流转）
□ 并发、幂等与竞态模型
□ 测试环境与数据
□ 风险识别与裁剪建议
```

### 2) 用例优先级门禁定义

```text
P0 门禁（发布阻断，通过率必须 100%）：
  - 主流程成功（Happy Path）
  - 核心数据写入/状态流转成功
  - 权限隔离不能破
  - 幂等性不能破
  - 核心数据删除/取消后无残留

P1 门禁（主要回归，通过率 >= 95%）：
  - 常见异常（参数错误、依赖失败）
  - 边界值（数值/长度/状态边界）
  - 状态变更（合法流转全覆盖）
  - Fallback / Retry 路径

P2 门禁（尽力通过）：
  - 极端边界/兼容性/性能退化
  - 低频风险组合
```

### 3) 风险裁剪决策参考

```yaml
risk_decision:
  必测:     # 风险高且成本低，或核心安全/数据完整性
  抽测:     # 风险中或成本高，抽样覆盖或自动化后补
  可延期:   # 风险低或依赖未就绪，标记后续迭代
  不覆盖:   # 有兜底机制或几乎不可能发生
```

## 可复用经验（方法论沉淀）

1. **先建模再写用例不是"多一步"，而是"省十步"**——建模阶段暴露的问题越多，执行阶段的意外就越少。
2. **模板的质量决定了产出质量的下限**——好的模板本身就是"隐形的评审者"，强迫使用者不遗漏关键维度。
3. **风险裁剪和"不覆盖"的决策比覆盖本身更重要**——清晰的裁剪理由能让团队把有限资源投入到最关键的地方。
4. **AI Skill 是方法论传播的高效载体**——传统方法论文档容易被存着吃灰，但 AI Skill 能在实际工作中"顺便"完成培训。

## 述职/面试可直接复用的话术

"我在测试设计方面做的最核心的一件事，不是写了多少用例，而是把测试设计本身做成了可复用的方法论。传统的测试设计靠经验和感觉，我把它改成了两阶段流程：第一阶段先系统性做风险建模，暴露所有可能出问题的地方；第二阶段再按优先级转成可执行的用例。这个方法论已经模板化并通过 AI Skill 集成到工具链中——新人不再需要从零摸索，团队的质量基线也不再依赖特定个人。"
