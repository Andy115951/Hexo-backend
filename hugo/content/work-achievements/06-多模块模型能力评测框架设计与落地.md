## 背景与问题定义

### 1) 业务场景

团队需要长期比较不同模型与版本，但单点测试无法覆盖真实能力全貌。需要一个“既能快跑日常回归，又能做深度对比”的统一评测平台。

### 2) 原始痛点

1. 测试维度分散，缺少统一评分逻辑。
2. 同一模型在不同测试下结论冲突，无法形成总评。
3. 报告格式不统一，结果难接入自动化流程。

### 3) 影响评估

- 决策效率低：每次对比都要重新组织测试集。
- 解释成本高：无法清晰说明“为什么这个模型更适合当前场景”。
- 监控能力弱：难以持续追踪质量变化。

---

## 我在这件事里实际做了什么

1. 我先把“模型评测”从一个大词拆成多个能力域，而不是继续堆一个总分无法解释的测试集合。
2. 我把综合评测和工具调用专项分成两层：一层解决“总体画像”，一层解决“关键能力深挖”，让框架既可横向比较，也能单点分析。
3. 我把评测规模设计成 `quick / standard / comprehensive` 三档，让它既适合开发时快测，也适合选型时深测。
4. 我把结果输出做成多格式和可归档产物，而不是只在控制台打印一次。
5. 我把评测体系、测试用例、评分规则、脚本入口、结果文件都沉淀进项目目录，让这套能力是可重复、可扩展、可接流程的。

---

## 目标与验收标准

### 1) 目标

1. 建立分模块评测架构，支持按需组合执行。
2. 建立模块权重和总分机制，输出可解释综合结论。
3. 支持多档测试规模，满足快测与深测需求。
4. 支持多格式报告输出，便于本地分析与平台集成。

### 2) 验收标准

- 具备四个核心模块并可独立执行。
- 总分按模块权重自动计算并可解释。
- 支持 `quick / standard / comprehensive` 三种规模。
- 报告至少支持 Console + JSON，并可扩展 HTML/Markdown。

---

## 约束与边界

- 约束 1：评测框架必须可扩展，不锁死具体模型或服务商。
- 约束 2：执行时长必须可控，适配日常开发节奏。
- 约束 3：评分体系需在“可解释性”和“自动化可执行性”间平衡。
- 非目标：本阶段不追求学术 benchmark 全覆盖，优先覆盖业务高相关能力。

---

## 核心原理与评测矩阵

### 1) 为什么这样设计

1. 先分能力域，再做综合结论：先分模块看短板，再加权看整体，能避免单项优势掩盖关键风险。
2. 快测与深测必须共存：日常回归需要快，关键决策需要深，统一框架下多档规模最实用。
3. 评测框架要与业务目标同构：模块和权重应对应真实业务风险，而不是只追求 benchmark 分数。
4. 报告体系必须兼容人读和机读：人需要可解释结论，系统需要结构化数据，二者缺一不可。

### 2) 当前真实评测矩阵

| 维度 | 真实落点 | 当前可见证据 |
| --- | --- | --- |
| 综合架构 | `framework/architecture.js` | 四大模块、权重、等级标准、三档规模 |
| 综合入口 | `framework/index.js` | `evaluate / compare / testToolCalling / testCoding` 等 API |
| 真实任务 | `framework/real-world-tasks.js` | GAIA 风格任务模块 |
| 代码能力 | `framework/coding-tests.js` | HumanEval 风格代码测试 |
| 产品能力 | `framework/chatbox-features.js` | Chatbox 特定功能测试 |
| 工具调用专项 | `tool-calling/` | 13 个用例、6 维评分、CLI 与报告输出 |
| 运行脚本 | `scripts/` | test-run、test-compare、visual-report 等 |
| 结果沉淀 | `evaluation-results/` | JSON/HTML/Markdown 多种真实输出 |

### 3) 原理流转图（简化）

```text
选择测试规模与模块
  -> 运行 toolCalling / realWorldTasks / coding / chatboxFeatures
    -> 模块得分归一化
      -> 按 moduleWeights 计算总分
        -> 生成 Console / JSON / HTML / Markdown 报告
          -> 进入选型、回归或对比流程
```

## 我的关键动作

### 1) 设计模块化评测架构

定义四大模块，并配置权重：

1. 工具调用能力（40%）
2. 真实任务完成（30%）
3. 代码能力（20%）
4. 业务特性能力（10%）

通过统一结果模型把模块分数汇总为可解释综合评分。

### 2) 设计多规模执行策略

为不同场景设计三档规模：

1. quick：快速校验，适合日常开发反馈。
2. standard：标准评估，适合周度回归与常规选型。
3. comprehensive：深度评估，适合关键决策与上线前验证。

核心价值是把“耗时成本”变成显式可选参数。

### 3) 建立工具调用专项评分体系

在工具调用模块中，我引入了 6 维度评分：

1. 工具选择
2. 参数准确性
3. 调用顺序
4. 返回值使用
5. 错误处理
6. 推理能力

并按难度分层测试用例（基础、中级、高级、专家），覆盖真实使用中的链式调用与异常分支。

### 4) 建立统一报告和对比能力

- 单模型评测：输出模块详情与总体等级。
- 多模型对比：统一基线下横向比较。
- 多格式报告：支持终端查看、机器读取、可视化展示。

---

## 难点、风险与应对

### 1) 难点

- 多模块评分容易出现“看起来全面但结论不聚焦”。
- 真实任务与可控 mock 测试在稳定性和真实性之间存在冲突。
- 规模一旦拉大，如果不做分档，就会让评测无法进入日常开发节奏。

### 2) 风险与应对

- 风险：模块权重设置不合理导致总分偏差。  
  应对：权重显式配置，并支持按业务阶段调整。
- 风险：测试集增长失控导致执行过慢。  
  应对：多规模运行机制 + 分层抽样策略。
- 风险：结果很多但难消费。  
  应对：统一报告生成器 + 多格式输出 + 历史结果目录。

### 3) 关键突破

- 从“单点测试集合”升级为“统一评测框架”。
- 从“结果碎片化”升级为“可解释综合评分”。
- 从“只能一次性比一比”升级为“可回归、可对比、可归档”的质量平台能力。

---

## 结果与影响

### 1) 短期结果

1. 建立统一评测入口，模型比较效率提升。
2. 测评结果可结构化输出，便于工程接入。
3. 综合评测与专项评测不再混在一起，分析粒度更清晰。

### 2) 中期价值

1. 模型选型决策具备一致标准和证据链。
2. 版本回归可持续执行，便于早期识别退化。
3. 后续新增能力域时，可以在既有框架下扩模块，而不是另起一套脚手架。

### 3) 长期复用价值

1. 框架可持续扩展新模块和新用例。
2. 可作为质量门禁与监控体系的基础能力。
3. 这套结构既能服务研发内测，也能服务产品层面的模型选型讨论。

## 可复用经验

1. 评测平台先做模块化，再做规模化，最后做可视化。
2. 总分必须可拆解，否则无法指导优化。
3. 真实任务与 mock 测试要组合使用，才能兼顾真实性和稳定性。
4. 评测框架的目标不是“跑很多题”，而是“支撑决策”。
