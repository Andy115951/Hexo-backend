## 背景与问题定义

### 1) 业务场景

在长会话中，用户设置了较小上下文窗口，但系统仍持续触发压缩，导致用户认知与系统行为不一致，反馈集中在“像 bug、不可理解、不可预期”。

### 2) 原始痛点

1. 团队讨论停留在“配置是否生效”，缺少统一机制视角。
2. 业务、产品、研发对“压缩触发条件”理解不一致。
3. 只有现象没有模型，难以制定可执行优化方案。

### 3) 影响评估

- 体验层：用户难理解为什么被压缩，信任感下降。
- 工程层：修改点不明确，容易“修一处坏一处”。
- 运营层：问题反复出现，沟通成本高。

---

## 我在这件事里实际做了什么

1. 我先把“上下文压缩”从一个笼统名词拆成两件不同的事：本次请求到底发送多少上下文，以及历史消息如何长期治理。
2. 我把问题从“感觉系统乱压缩”转成机制分析：先看阈值计算，再看模型 contextWindow 来源，再看 tool-call 清理和 compaction point 边界。
3. 我没有只给一个拍脑袋方案，而是对比了全局压缩、仅窗口压缩、渐进式压缩这几类路径，明确各自收益与代价。
4. 我把讨论沉淀成了可落 PRD、阈值公式、边界数据结构和测试锚点，让后续实现和验收不再靠口头理解。
5. 我把“用户配置为什么看起来没生效”这类争议，收敛到具体 root cause：contextWindow 的来源不一致、tool-call 清理顺序、boundary message 的上下文构建方式。

## 核心原理与机制矩阵

### 1) 为什么这样设计

1. 请求窗口预算与历史存储预算必须分离：本次发送多少，和长期保留多少，是两类不同约束。
2. 压缩要遵循冷热分层：活跃区保真、半活跃区摘要化、冷区渐进治理，才能同时兼顾体验和成本。
3. 压缩必须可恢复：通过 summary message 和 compaction point 保留追溯路径，避免压缩后语义不可还原。
4. 触发机制需要稳定阈值与统一 contextWindow 来源：否则 UI、配置和触发行为会彼此打架。

### 3) 原理流转图（简化）

```text
会话新增内容
  -> 先清理旧 tool 调用上下文

      -> 超预算：触发 compaction
      -> 未超预算：维持当前状态
  -> 通过 compaction point 记录边界
  -> 动态构建发送给 AI 的上下文
```

## 我的关键动作

### 1) 从“抱怨描述”到“机制拆解”

我先把问题拆成两条链路：

1. 发送链路：控制本次请求携带哪些上下文。
2. 存储链路：控制整段历史如何压缩和保留。

关键结论：用户配置通常只影响发送窗口，不必然等于存储不压缩。这是认知偏差的核心来源。

### 2) 进行策略对照，避免单结论误导

我做了三种策略对照：

1. 全局压缩优先  
   优势：控体积强。  
   代价：可能压到用户仍关心内容。

2. 仅窗口内压缩  
   优势：直觉一致性高。  
   代价：历史膨胀风险高，长期恢复能力弱。

3. 渐进式压缩（推荐）  
   优势：活跃区优先保护，旧历史分段治理。  
   代价：实现复杂度更高，需要更多观测指标。

### 3) 定义渐进式压缩落地框架

- 第一层：活跃消息区轻量压缩，保证当前对话连续性。
- 第二层：半活跃区做摘要化与锚点保留。
- 第三层：冷历史区按阈值批量治理。

同时定义了“可恢复锚点”原则，避免压缩后彻底不可追溯。

### 4) 补齐可验证指标

我给出三类验收指标建议：

1. 体验一致性：压缩行为是否与用户配置预期一致。
2. 存储治理：历史增长曲线是否可控。
3. 可恢复性：压缩后是否可通过锚点恢复关键上下文。

## 难点、风险与应对

### 1) 难点

- 同一“压缩”在不同层语义不同，沟通极易错位。
- 只优化单一目标会导致其他目标退化。
- UI、provider settings、builtin model registry 三方如果不统一，就会持续制造“看起来像 bug”的体验问题。

### 2) 风险与应对

- 风险：过度压缩影响对话连续性。  
  应对：活跃区优先保护 + 渐进式策略。
- 风险：策略复杂后难以解释。  
  应对：分层术语标准化 + 触发链路图可视化。
- 风险：只修补触发逻辑，不管上下文构建边界。  
  应对：同时验证 tool-call 清理、summary message 和 compaction point。

### 3) 关键突破

- 把“配置争议”转为“机制分层问题”。
- 把“拍脑袋优化”转为“指标驱动优化”。
- 把“像 bug”变成“可以被阈值、边界、测试解释的工程问题”。

## 2026-08 知识补充：Prompt Cache 稳定性与分块窗口迁移

### 1) 这解决的不是回答质量问题，而是重复上下文的计算成本问题

模型提供方的 Prompt Cache 复用请求开头完全一致的上下文。一次新消息必然会增加新的尾部内容；优化目标不是让整份请求不变，而是让系统提示词和已有历史尽可能保持同一前缀，以复用已计算的 token，降低首 token 延迟和重复输入成本。

```text
稳定系统提示词 + 已有历史消息  <- 可复用的缓存前缀
本轮用户输入 / 临时运行时信息 <- 每次新增的尾部
```

### 2) 1.21 / 1.22 的两类前缀漂移

#### 日期漂移

旧版聊天模式在每次请求的系统提示词开头构造：

```text
Current model: <model>
Current date: <当天日期>
Additional info for this conversation: ...
```

同一天内日期不变时，这一项本身不会造成 miss；跨 0 点后日期变化，动态字段位于请求头部，会让整段缓存前缀失效。旧版没有按间隔插入的实时 `<system-reminder>`，而是每次都带“当天日期”。

#### 窗口逐条滑动

当 `maxContextMessageCount` 超限时，旧实现每轮都丢弃最早的一条消息。历史开头因此每发一条就变化一次；即使没有跨日期，超限后的连续对话仍会持续损失历史前缀缓存。

### 3) 1.23 的实现：冻结前缀，把实时信息放到尾部

聊天模式改为保留用户系统提示词在最前，运行时块放在后面，并把时间冻结到会话起点：

```text
用户系统提示词 + 稳定指令
## Runtime
Current model: <model>
Conversation started: <会话开始时间>
```

工作模式对应的是 `Session context captured: <快照时间>`。同一会话跨日期、跨分钟或时区变化时，以上时间不变，因此不再因为“今天日期”改写前缀。

实时当前时间仍会在有必要时提供给模型：某条用户消息与上一条有效消息相隔至少 30 分钟，或隔很久重新生成 / 恢复任务时，客户端在请求构造阶段临时添加：

```text
<system-reminder>
Current date and time: <实时日期时间>
</system-reminder>
```

它位于续聊 turn 的尾部，不写入会话存储或时间线，因此不会改动既有缓存前缀。普通“隔久续聊”场景使用该用户消息自身的持久化时间戳；以后重建历史时会在相同位置生成相同内容，仍可保持稳定。

### 4) 分块窗口迁移：用少量历史换取连续命中

新实现不再超限就逐条移动窗口，而是按约四分之一窗口批量前移：

```ts
const effectiveLimit = maxContextMessageCount + 1 // 当前输入额外保留
const chunk = Math.max(1, Math.ceil(effectiveLimit / 4))
const dropCount = Math.ceil(overflow / chunk) * chunk
```

例如上限为 10 条历史时，`effectiveLimit = 11`，块大小为 `ceil(11 / 4) = 3`：第一次超限会一次丢掉最早 3 条，后续几轮保持同一个历史起点，直到超过下一个块阈值才再次移动。刚完成一次批量移动时会短暂少带少量旧历史，但不会超过用户设定的窗口；交换到的是超限后多轮请求的缓存前缀稳定性。

```text
旧版：每轮丢 1 条 -> 每轮历史开头变化 -> 连续 miss
新版：一次丢 1 块 -> 后续数轮历史开头不动 -> 可复用缓存
```

### 5) 验收与边界

1. 跨 0 点继续同一聊天会话：`Conversation started` 应保持会话起点，不再出现会变的 `Current date: 当天日期`。
2. 连续快速对话：不应出现实际的 `Current date and time` 提醒。
3. 间隔至少 30 分钟续聊：请求的用户 turn 尾部应有完整的 `<system-reminder>` 当前时间块。
4. 小消息窗口持续发送：历史起点应分块变化，不应每轮向前滑动一条。
5. 这是一项缓存优化，不保证所有请求都命中：改系统提示词、切模型、改变 Soul / Memory / 工作目录、工具集变化、提供方 TTL 到期等仍可合理导致 miss。
