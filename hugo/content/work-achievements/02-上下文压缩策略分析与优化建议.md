## 背景与问题定义

### 1) 业务场景

在长会话中，用户设置了较小上下文窗口，但系统仍持续触发压缩，导致用户认知与系统行为不一致，反馈集中在“像 bug、不可理解、不可预期”。

### 2) 原始痛点

1. 团队讨论停留在“配置是否生效”，缺少统一机制视角。
2. 业务、产品、研发对“压缩触发条件”理解不一致。
3. 只有现象没有模型，难以制定可执行优化方案。

### 3) 影响评估

- 体验层：用户难理解为什么被压缩，信任感下降。
- 工程层：修改点不明确，容易“修一处坏一处”。
- 运营层：问题反复出现，沟通成本高。

---

## 我在这件事里实际做了什么

1. 我先把“上下文压缩”从一个笼统名词拆成两件不同的事：本次请求到底发送多少上下文，以及历史消息如何长期治理。
2. 我把问题从“感觉系统乱压缩”转成机制分析：先看阈值计算，再看模型 contextWindow 来源，再看 tool-call 清理和 compaction point 边界。
3. 我没有只给一个拍脑袋方案，而是对比了全局压缩、仅窗口压缩、渐进式压缩这几类路径，明确各自收益与代价。
4. 我把讨论沉淀成了可落 PRD、阈值公式、边界数据结构和测试锚点，让后续实现和验收不再靠口头理解。
5. 我把“用户配置为什么看起来没生效”这类争议，收敛到具体 root cause：contextWindow 的来源不一致、tool-call 清理顺序、boundary message 的上下文构建方式。

### 1) 目标

1. 明确压缩触发链路和配置作用边界。

### 2) 验收标准

- 团队对“请求窗口控制”与“全局存储压缩”定义一致。
- 每种策略都给出适用场景、风险和验证指标。
- 优化方案包含实现优先级、观测点和回退条件。

## 约束与边界

- 约束 1：压缩策略必须兼顾体验、成本、性能三方目标。
- 约束 2：会话历史具有长期价值，不能简单粗暴删除。
- 约束 3：系统需支持可恢复与可追溯，不可只追求体积最小。
- 非目标：本次不直接重写全量实现，先完成机制拆解与方案收敛。

## 核心原理与机制矩阵

### 1) 为什么这样设计

1. 请求窗口预算与历史存储预算必须分离：本次发送多少，和长期保留多少，是两类不同约束。
2. 压缩要遵循冷热分层：活跃区保真、半活跃区摘要化、冷区渐进治理，才能同时兼顾体验和成本。
3. 压缩必须可恢复：通过 summary message 和 compaction point 保留追溯路径，避免压缩后语义不可还原。
4. 触发机制需要稳定阈值与统一 contextWindow 来源：否则 UI、配置和触发行为会彼此打架。

### 2) 当前真实机制矩阵

| 上下文构建 | `src/renderer/packages/context-management/attachment-payload.ts` | 支持 `keepToolCallRounds = 2`、动态剔除旧 tool 调用 |

### 3) 原理流转图（简化）

```text
会话新增内容
  -> 先清理旧 tool 调用上下文
    -> 根据 contextWindow 和阈值判断是否 overflow
      -> 超预算：触发 compaction
      -> 未超预算：维持当前状态
  -> 通过 compaction point 记录边界
  -> 动态构建发送给 AI 的上下文
```

## 我的关键动作

### 1) 从“抱怨描述”到“机制拆解”

我先把问题拆成两条链路：

1. 发送链路：控制本次请求携带哪些上下文。
2. 存储链路：控制整段历史如何压缩和保留。

关键结论：用户配置通常只影响发送窗口，不必然等于存储不压缩。这是认知偏差的核心来源。

### 2) 进行策略对照，避免单结论误导

我做了三种策略对照：

1. 全局压缩优先  
   优势：控体积强。  
   代价：可能压到用户仍关心内容。

2. 仅窗口内压缩  
   优势：直觉一致性高。  
   代价：历史膨胀风险高，长期恢复能力弱。

3. 渐进式压缩（推荐）  
   优势：活跃区优先保护，旧历史分段治理。  
   代价：实现复杂度更高，需要更多观测指标。

### 3) 定义渐进式压缩落地框架

- 第一层：活跃消息区轻量压缩，保证当前对话连续性。
- 第二层：半活跃区做摘要化与锚点保留。
- 第三层：冷历史区按阈值批量治理。

同时定义了“可恢复锚点”原则，避免压缩后彻底不可追溯。

### 4) 补齐可验证指标

我给出三类验收指标建议：

1. 体验一致性：压缩行为是否与用户配置预期一致。
2. 存储治理：历史增长曲线是否可控。
3. 可恢复性：压缩后是否可通过锚点恢复关键上下文。

## 难点、风险与应对

### 1) 难点

- 同一“压缩”在不同层语义不同，沟通极易错位。
- 只优化单一目标会导致其他目标退化。
- UI、provider settings、builtin model registry 三方如果不统一，就会持续制造“看起来像 bug”的体验问题。

### 2) 风险与应对

- 风险：过度压缩影响对话连续性。  
  应对：活跃区优先保护 + 渐进式策略。
- 风险：策略复杂后难以解释。  
  应对：分层术语标准化 + 触发链路图可视化。
- 风险：只修补触发逻辑，不管上下文构建边界。  
  应对：同时验证 tool-call 清理、summary message 和 compaction point。

### 3) 关键突破

- 把“配置争议”转为“机制分层问题”。
- 把“拍脑袋优化”转为“指标驱动优化”。
- 把“像 bug”变成“可以被阈值、边界、测试解释的工程问题”。

---

## 结果与影响

### 1) 短期结果

1. 团队在机制定义上形成统一语言和共识。
2. 优化方向从“猜原因”变成“按链路改进”。
3. 压缩问题可以落到具体实现文件、PRD 和测试上讨论，而不再只靠现象复述。

### 2) 中期价值

1. 后续实现可按阶段推进，降低一次性改动风险。
2. 验收标准清晰，避免重复争论“到底算不算修好”。
3. 未来继续扩展压缩 UX、tool 清理或 contextWindow 获取时，都有统一母框架可复用。

### 3) 长期复用价值

1. 上下文治理形成可复用方法论，可迁移到其他长会话系统。
2. 为后续容量规划、体验优化提供统一框架。
3. 让“上下文管理”从功能细节，升级成产品体验与架构协同问题来治理。
