- skill 已把 dev 模式默认路径收敛到 `pnpm start:cdp` + 端口 `9333`，并明确禁止静默回退到 `9222` 或安装版。

一句话判断：这次工作的价值不是“给 AI 多喂点上下文”，而是把框架知识压成一份可验证、可维护、可直接约束生成结果的工程资产。

---

## 背景与问题定义

### 1) 业务场景

Chatbox 桌面端自动化测试项目已经运行多个迭代，沉淀了分层框架（framework-v2）、运行配置（Electron/CDP）、选择器体系、动作封装等大量基础设施。但这些知识散落在代码、文档和团队成员的经验中，没有一个统一的入口可以快速获取完整的上下文。

### 2) 原始痛点

1. **写测试需要"懂很多"**：新人写一条测试用例前，需要理解框架分层结构、两种启动模式的区别、选择器的定位策略、动作 API 的调用约定——光是"把环境跑通"就可能花半天。
2. **框架知识靠传帮带**：框架架构的设计原因（为什么分层、为什么用 ChatboxActionsV2 作为统一入口、什么时候用 Electron 模式 vs CDP 模式）没有人文档化，每次回答类似问题都在重复解释。
3. **AI 生成测试代码质量不可控**：直接让 AI 写测试，它可能忽略框架约定——比如直接访问 Playwright API 而不是通过 ChatboxActionsV2、使用错误的启动方式、不清理环境变量 `ELECTRON_RUN_AS_NODE`。
4. **测试管理管道分散**：YAML 用例数据源、HTML 看板、脚本生成器各自独立，缺少统一的管理视图。

### 3) 影响评估

- **效率损失**：每次写测试平均需要 20-30 分钟查阅代码和文档来确认 API 用法。
- **质量风险**：AI 生成的测试代码可能不符合框架规范，引入维护负担。
- **认知负载**：团队成员需要记忆大量框架细节才能高效工作。

---

## 我在这件事里实际做了什么

为了让 AI 写测试时不再“像是知道框架，但总会偏一点”，我实际做了五类工作：

1. **把框架重新拆给 AI 看**：从 `framework-v2` 的 core、selectors、actions 和主入口重新梳理职责，而不是直接把代码目录甩给 AI。
2. **把隐性规则显式写出来**：例如 dev 场景默认 `9333`、不能静默回退安装版、必须删除 `ELECTRON_RUN_AS_NODE`、必须使用 `ChatboxActionsV2`。
3. **把使用路径按任务意图组织**：不是按模块给 AI 灌输信息，而是按“如何启动、怎么选模式、怎么找 selector、怎么组织测试文件”来编排技能内容。
4. **把 skill 部署到实际工作入口**：同时放到 `.claude/skills` 和 `.trae/skills`，让它不是仓库外的一份孤立文档。
5. **用真实生成任务倒逼技能收敛**：根据 AI 生成测试时暴露的问题回补技能内容，而不是靠主观想象补文档。

## 目标与验收标准

### 1) 目标

1. 将自动化测试框架的核心知识编码成 AI 可读的结构化技能文件。
2. AI 在技能引导下能生成符合框架规范的测试代码（使用正确的 API、启动模式、文件组织）。
3. 技能文件本身成为团队的知识入口，新人通过阅读它即可理解框架全貌。
4. 技能可持续维护，框架演进时同步更新。

### 2) 验收标准

- 技能文件覆盖框架架构总览（core/selectors/actions/tests 分层）和运行原理。
- 技能文件包含完整的 API 参考（message/model/sidebar/network/settings 各域的可用方法、参数、返回值）。
- 技能文件明确两种启动模式（Electron Launch vs CDP Connection）的使用场景和代码示例，并将 `chatbox-pro` 开发态默认路径收敛到 `pnpm start:cdp` + `9333`。
- 技能文件包含选择器编写规范和测试文件组织规则。
- AI 根据技能文件生成的测试代码通过框架的 lint/type-check。

---

## 约束与边界

- 约束 1：技能文件必须是自包含的——不依赖外部链接，AI 读取一个文件就能获得完整上下文。
- 约束 2：技能内容必须可验证——不能包含臆造的 API 或架构描述，每段内容都来自实际代码。
- 约束 3：不能暴露敏感信息（认证 token、内部 URL）。
- 非目标：不修改框架本身的设计，只做知识的整理和编码。

---

## 核心原理（为什么这样设计）

1. **AI 知识库的核心是"上下文完整性"**
   AI 在生成代码时，如果缺少关键上下文（如启动模式的选择、API 的边界条件），输出质量会大幅退化。技能文件的核心价值不是"教 AI 写代码"，而是"给 AI 提供做出正确决策所需的完整上下文"。

2. **知识结构必须反映框架的实际使用路径**
   技能文件不应该按"代码模块"组织（core → selectors → actions），而应该按"用户的提问意图"组织（启动配置 → 选择器查找 → API 调用 → 文件组织）。前者是代码视角，后者是使用视角。

3. **框架的约束条件必须显式化**
   框架中很多"大家都知道的规矩"——比如必须先 delete `ELECTRON_RUN_AS_NODE`、必须用 ChatboxActionsV2 作为入口、serial 模式的必要性——对 AI 来说是盲区。技能文件必须把这些隐性约束显式列出来。

4. **技能文件本身就是文档资产**
   即使不用 AI，团队成员也可以把技能文件作为框架的快速入门文档。这意味着：文档要够清晰、够完整、够新。

### 知识流转图

```text
框架代码（source of truth）
  -> 人工提取架构知识（分层/API/启动模式/约束）
    -> 编码为结构化 SKILL.md
      -> AI 读取技能文件
        -> 获得完整上下文 + 约束条件
          -> 生成符合框架规范的测试代码
      -> 团队成员阅读技能文件
        -> 快速理解框架全貌和使用方式
```

## 我的关键动作

### 1) 框架知识梳理与抽象

- **通读框架所有核心模块**：重新审视 framework-v2 的分层设计，理解每个 layer 的职责和设计意图（core 控制生命周期、selectors 隔离 UI 细节、actions 封装业务操作、tests 只关注业务验证）。
- **梳理 ChatboxActionsV2 所有公开 API**：逐方法记录签名、参数、返回值、使用场景和注意事项，确保技能文件中没有遗漏或过时的 API。
- **总结两种启动模式的适用场景**：Electron Launch 用于打包后的应用测试；CDP Connection 用于 `chatbox-pro` 开发调试，其中标准路径是 `pnpm start:cdp` + `9333`，不应在 dev 场景中静默回退到安装版。

### 2) 技能文件编写与结构化

- **设计技能文件的目录结构**：按使用场景而非代码模块组织——启动方式 → API 参考 → 选择器规则 → 文件组织 → 测试管理管道。
- **编写完整的 API 参考章节**：将 message/model/sidebar/network/settings 五个域的可用方法逐一列出，包含每个方法的作用、参数类型、返回值、代码示例。
- **显式化隐性约束**：将 `delete process.env.ELECTRON_RUN_AS_NODE`、`test.describe.configure({ mode: 'serial' })`、统一入口原则等框架约定写成独立条目。
- **文档化选择器优先级**：`aria-label` > `data-testid` > CSS class patterns > `getByText()`，并给出每种选择器在 Chatbox 中的实际使用示例。

### 3) 技能部署与验证

- **将技能文件部署到项目 .claude/skills/ 目录**：确保 AI 在该项目目录下工作时自动获得技能上下文。
- **在 .trae/skills/ 目录维护独立副本**：适配不同 AI 工具（Trae）的读取路径。
- **用实际测试生成验证技能效果**：按照技能文件的引导让 AI 生成测试代码，验证生成的代码是否遵守框架约定、使用正确的 API、文件命名和目录放置是否规范。
- **根据验证结果迭代技能内容**：补充缺失的 API 细节、修正模糊的描述、增加更多代码示例。

### 4) 测试管理管道文档化

- **将 YAML 数据源、HTML 看板、脚本生成器的关系整理成清晰的流程图**。
- **记录 test-cases.yaml 的字段结构和录入规则**，使新用例的添加有标准可循。
- **文档化服务启动命令和看板访问方式**，降低团队的搭建成本。

## 难点、风险与应对

### 1) 难点

- **知识提取的完整性问题**：框架中有太多"理所当然"的约定——当你每天都用它时，你不会意识到这些信息对 AI 来说是盲区。需要通过反复测试 AI 生成的结果来发现缺失的信息。
- **多平台兼容（.claude + .trae）**：两个 AI 工具的技能加载路径和机制不同，需要维护两份技能文件或使用符号链接。

### 2) 风险与应对

- **风险**：技能内容与框架代码不同步，框架更新后技能过时。  
  **应对**：将技能维护纳入框架变更流程——任何框架接口变更同步更新技能文件中的对应 API 参考。
- **风险**：AI 生成代码过于依赖技能文件，但技能描述的准确性不足。  
  **应对**：用实际 AI 生成结果作为技能质量的验收标准，发现偏差立即修正。

### 3) 关键突破

- **从"写代码"到"做知识工程"的认知升级**：传统自动化测试关注的是"怎么把测试写对"，这次做的是"怎么让 AI 帮我们把测试写对"——本质是把自己的知识编码为 AI 可用的资产。
- **隐性知识显式化的方法论**：第一次系统性地把大脑中的框架上下文提取为结构化文档，不仅对 AI 有用，对团队的知识传承也有很大价值。

## 关键约束显式化清单（这是 skill 最值钱的部分）

我认为这份 skill 最有含金量的，不是列了多少 API，而是把下面这些“团队成员默认知道、AI 默认不知道”的约束显式写了出来：

1. 测 `chatbox-pro` dev 时，默认走 `connectCDP({ port: 9333 })`，而不是模糊地“试试哪个端口能通”。
2. dev 场景下如果 `9333` 不可用，要明确报错，不允许静默回退到 `9222` 或安装版。
3. Electron 场景必须先 `delete process.env.ELECTRON_RUN_AS_NODE`。
4. 测试代码必须通过 `ChatboxActionsV2` 访问能力，不能直接在 spec 里到处写 `page.locator()`。
5. Electron 测试默认要用 `test.describe.configure({ mode: 'serial' })`。
6. CDP 断开不等于关闭应用，`chatbox.close()` 只会断开连接。

这些约束一旦不显式写出来，AI 很容易生成“看起来像对的，但放进项目里就不合规范”的代码。

### 2) 启动模式对比（技能核心内容示例）

```ts
// Electron Launch（打包应用——适用于回归和 CI）
const chatbox = new ChatboxActionsV2();
await chatbox.launch('/Applications/Chatbox.app/Contents/MacOS/Chatbox');

// CDP Connection（开发/调试——chatbox-pro 标准路径）
const chatbox = new ChatboxActionsV2();
await chatbox.connectCDP({ port: 9333 });  // dev mode
// 历史上也兼容过手动实例端口，但当前技能默认不再自动回退到 9222
```

### 3) 框架入口封装（ChatboxActionsV2 的设计理念）

```ts
// 所有测试只能通过 ChatboxActionsV2 访问 Playwright API
// 不允许在 spec 文件中直接使用 page.locator()、page.click() 等

// ✅ 正确
await chatbox.message.sendMessage('你好');
await chatbox.model.selectByName('GPT-4');

// ❌ 错误（绕过框架封装）
await page.locator('.input-area').fill('你好');
await page.locator('.model-selector').click();
```

### 4) 测试文件规范

```text
tests/
├── smoke/            # 冒烟测试（快速验证核心功能）
├── regression/       # 回归测试（功能级全覆盖）
├── electron/         # Electron 特定测试（启动/窗口/菜单）
├── debug/            # 调试用测试模板
└── experiments/      # 实验性测试（新技术方案验证）

命名规则：{功能域}-{场景描述}.spec.ts
例如：message-send-and-receive.spec.ts
```

## 可复用经验（方法论沉淀）

1. **AI 技能的编码原则：上下文完整性 > 信息量**——技能文件不需要面面俱到，但必须保证 AI 做出正确决策所需的关键上下文都在。
2. **隐性约束显式化是技能工程的核心难点**——"大家都知道的事"对 AI 是盲区。识别这些隐性约束最好的方法是用 AI 生成一次代码，看它在哪出了问题。
3. **技能文件 = 活文档**——技能文件不应该是一份"额外"的文档，而应该是框架知识的权威入口。如果框架的内容有变化，第一件事就是更新技能文件。
4. **存量的框架代码是最好的知识源**——写技能文件不是靠回忆，而是靠重新阅读代码、理解设计意图、验证 API 行为。

## 述职/面试可直接复用的话术

"我做的不仅仅是写自动化测试脚本，而是把整个自动化测试框架的知识体系做成了 AI 可以理解和执行的技能资产。传统的 AI 辅助测试生成的问题是：AI 不了解框架的设计约束，生成的代码经常不符合规范。我通过把框架的分层架构、API 约定、启动模式、选择器策略等知识结构化编码，让 AI 第一次就能生成符合框架规范的测试代码——这相当于把团队积累的框架使用经验变成了一个可调用的、持续可维护的知识资产。"
