## 背景与问题定义

在 Chatbox 备份导入与“找回对话列表”场景中，用户侧会出现几类典型问题：

1. 备份 JSON 能导入，但会话列表恢复失败。
2. 导出的备份结构被手工修改后，无法判断到底坏在哪。
3. 只有 HTML 或文本形式的聊天记录，没有标准 JSON 备份。
4. 支持同学需要靠人工打开 JSON 一条条找问题，效率低且不可复用。

这类问题表面上都叫“导入失败”，但本质并不相同：

- 有的是 `session:*` 结构缺字段
- 有的是 `chat-sessions-list` 元数据缺失
- 有的是消息结构不符合当前导入 schema
- 有的是根本没有备份 JSON，只剩 HTML / Markdown / 文本导出稿

如果没有工具，这类问题只能靠支持同学临时修、临时解释、临时重试，无法沉淀成标准能力。

---

## 我在这件事里实际做了什么

为了把它从“数据救援”做成“可复用恢复能力”，我做了四类工作：

1. **先把失败原因收敛成结构化规则**：区分顶层导出字段、`session:*`、`messages[]`、`chat-sessions-list` 四层问题，不再把所有导入失败混成一类。
2. **补一套可自动修复的 JSON 校验器**：支持只检查、自动修复、重建 `chat-sessions-list`、重新导出修复结果。
3. **补一套恢复入口**：把 Chatbox 导出的 HTML，以及带角色标记的 Markdown / 纯文本，对话恢复成可导入的单会话 JSON。
4. **把支持动作产品化**：不是只留脚本，而是做了浏览器本地网页，让支持和排查都可以直接使用。

---

## 核心产出

### 1) 备份检测 / 修复 CLI

补了可执行的本地校验工具，用于：

- 检查备份 JSON 结构是否合法
- 输出问题列表
- 自动补齐缺失字段
- 选择性重建 `chat-sessions-list`
- 导出修复后的新 JSON

这个阶段的意义，是先把“修规则”收敛成可执行逻辑，而不是只写分析结论。

### 2) 网页版备份检测 / 修复工具

在 CLI 规则稳定后，进一步做了网页版入口：

- 上传本地备份 JSON
- 本地展示 errors / warnings / fixable
- 一键自动修复
- 下载修复后的 JSON

关键取舍是：**所有处理默认都在浏览器本地完成**，避免把用户备份上传到服务端，降低支持场景的顾虑。

### 3) 对话恢复工具：HTML / MD / TXT -> 导入 JSON

除了“修坏备份”，还补了一条“从非标准导出稿恢复”的路径。

支持三类来源：

1. Chatbox 导出的 HTML
2. 带 `USER:` / `ASSISTANT:` / `SYSTEM:` 标记的 Markdown
3. 带角色分段的纯文本对话稿

恢复结果统一输出成 Chatbox 可导入的单会话备份结构：

- `session:*`
- `chat-sessions-list`
- `configVersion`
- `__exported_items`
- `__exported_at`

### 4) 文本恢复规则的边界修正

在真实文件验证时，又补了两类关键边界：

1. **Markdown 三引号包裹问题**  
很多导出稿是：

````md
**user**:

```text
消息内容
```
````

如果不做特殊处理，三引号会被错误写进消息正文。

2. **纯文本角色前缀问题**  
有些 txt 不是标准 `USER:`，而是 `▶ USER:`、`▶ ASSISTANT:` 这类格式。  
旧规则会把整篇吞成一条大消息，修完后才能正常切成多轮消息。

## 一个典型案例：从“导入失败”到“规则化修复”

这次工作里有一个典型坏备份样本，核心特征是：

- 共有 `117` 条 session 记录
- `chat-sessions-list` 整体缺失
- 多条 `session:*` 记录缺少顶层 `id`
- 一部分记录是空壳对象或缺少 `messages`

在旧方式下，这类问题需要：

1. 手工打开 JSON
2. 靠经验判断哪个字段缺了
3. 尝试修改
4. 反复导入验证

而在新工具下，可以直接得到结构化诊断，并按规则修复 / 重建。

这类案例说明，真正有价值的不是“我会手改 JSON”，而是我把人工判断抽象成了工具规则。

## 关键设计原则

### 1) 先保守修复，再追求自动化

自动修复只处理结构性、可推断的问题，例如：

- 缺失 `session.id`
- 缺失 `messages`
- 缺失 `settings`
- `chat-sessions-list` 缺失或和 session 对不上

真正无法凭空恢复的内容，例如图片二进制缺失，不做“伪修复”，只给出提醒。

### 2) 单独区分“校验”和“恢复”

不是所有问题都应该直接修：

- “校验”负责解释哪里坏了
- “修复”负责生成新 JSON
- “恢复”负责把非 JSON 对话稿转成标准备份

这能避免工具混成一个黑盒按钮。

### 3) 尽量浏览器本地处理

用户备份和聊天记录属于高敏感数据。  
把处理逻辑放在浏览器本地，既降低安全顾虑，也更适合一线支持同学直接发给用户使用。

## 难点、风险与应对

### 1) 关键难点

- 同样叫“导入失败”，实际根因差异很大，必须先分层抽象。
- 有些字段可以推断修复，有些内容本质上已经丢失，边界必须讲清楚。
- HTML / Markdown / 文本三类输入格式差异大，不能用单一解析规则硬套。

### 2) 风险与预案

- 风险 A：自动修复过度，写出“看起来能导入、实际上语义更坏”的结果  
  应对：仅修结构，不伪造无法恢复的真实内容。

- 风险 B：网页工具被误认为会上传文件  
  应对：明确本地处理模型，页面和文档都说明不上传。

- 风险 C：文本恢复规则过窄，真实稿件切段不准  
  应对：用真实 md / txt 文件持续修边界，而不是只拿理想样例自测。

### 2) 备份问题是怎么分层抽象出来的

最开始最大的坑，是“导入失败”这四个字太宽泛。

如果不先分层，后面所有修复都会混在一起，工具也会变成一个巨大的 if/else 黑盒。

这次最终把问题收敛成四层：

#### 第一层：顶层导出字段

主要包括：

- `__exported_items`
- `__exported_at`
- `configVersion`

这类问题通常不会直接导致某条具体消息坏掉，但会影响导入器对整体文件的基本判断。

#### 第二层：`session:*`

这是最关键的一层，因为导入恢复最终还是围绕会话对象。

主要关注：

- session 是否是对象
- 顶层 `id` 是否存在
- `id` 是否和存储键匹配
- `type` 是否合法
- `name` 是否为空
- `messages` 是否存在且是数组
- `settings` / `messageForksHash` 是否是对象

#### 第三层：`messages[]`

这里关注的是单条消息是否合法：

- 消息是否是对象
- 是否缺 `id`
- `role` 是否合法
- `timestamp` 是否是数字
- `contentParts` 是否存在
- 旧版 `content` 是否需要迁移
- 图片 part 是否缺 `storageKey` / `url`

#### 第四层：`chat-sessions-list`

这层是“列表能不能正常显示 / 找回”的关键：

- 整个列表是否缺失
- 单条 meta 是否有效
- meta 里是否缺 `id`
- 是否存在孤儿 meta
- `type` / `name` / `sortOrder` / `createdAt` 是否缺失
- 是否有 session 存在但 meta 没同步生成

把问题拆成这四层之后，很多事情立刻就清晰了：

1. 某些问题属于“可自动补字段”
2. 某些问题属于“应重建 meta list”
3. 某些问题属于“只能提示，不应该伪造”

### 3) 为什么会盯上 `session.id` 和 `chat-sessions-list`

这次一个特别关键的发现是：

- 有些坏文件不是“所有数据都坏了”
- 而是 session 本身还在，但元数据列表恢复失败

其中一个典型根因，就是 `session:*` 记录里虽然键名带了 id，但对象顶层缺少 `id` 字段。

这个问题在“找回对话列表”路径里会被放大，因为恢复逻辑会扫描所有 `session:*`，再把它们写回 `chat-sessions-list` 对应的存储。

也就是说：

```text
session:* 能读到
  -> 尝试提取 meta
  -> meta 依赖 id
  -> 顶层 id 缺失
  -> 写列表失败
  -> 用户看到“恢复失败”
```

这个发现的重要性在于：

- 它不是前端展示问题
- 也不是导入器完全拒绝文件
- 而是“恢复列表”这个阶段被卡住了

所以工具里必须把“重建 `chat-sessions-list`”单独做成一个明确能力，而不是顺手补一下字段就算了。

### 4) 典型坏样本为什么值得单独记住

这次最值得保留记忆的一个坏样本特征是：

- `117` 条 session
- `chat-sessions-list = 0`
- 大量 session 缺顶层 `id`
- 一部分 `messages` 缺失
- 一部分对象几乎是空壳

这个样本的意义不是“数字很大”，而是它完整覆盖了支持场景里最麻烦的几类问题：

1. 文件不是完全损坏，而是“半坏”
2. 表面上有很多数据，但列表恢复不出来
3. 不是靠补一个字段就能全部解决
4. 很适合作为规则验证样本

以后如果继续做这条线，最好保留这种“高噪声真实坏样本”作为回归测试输入，而不是只拿干净示例。

### 5) CLI 为什么先做，网页为什么后做

这次顺序上其实是有意的：

#### 先做 CLI

原因是：

- 规则还没收敛时，命令行更适合快速迭代
- 输出可以更原始，便于看 errors / warnings / fixable 的真实分布
- 更适合先拿坏样本做重复试验

CLI 阶段更像是在回答：

- 哪些规则是稳定的？
- 哪些问题应该报 error，哪些只是 warning？
- 哪些自动修复是可靠的？

#### 再做网页

网页阶段解决的是另一个问题：

- 支持同学 / 自己未来复用时，不能每次都跑命令
- 需要一个更低门槛、更直观的入口
- 要把“本地处理、不上传文件”这个特性显式表达出来

所以网页不是 CLI 的替代，而是规则成熟后的交付层。

---

### 6) 为什么坚持“浏览器本地处理”

这件事一定要记一下，因为这是这条工具线的一个非常明确的产品取舍。

原因主要有三点：

#### 1. 用户数据敏感

备份 JSON 和对话导出稿本质上都可能包含：

- 个人隐私
- 商业信息
- 工作对话
- 附件引用信息

一旦做成“上传到服务端再解析”，支持场景里就会天然多一层安全顾虑。

#### 2. 这类工具不需要服务端算力

JSON 校验、字段补齐、文本切段、结构组装，本身都属于轻量计算，浏览器本地足够处理。

#### 3. 更适合发给别人直接用

“打开网页 -> 选文件 -> 本地修 -> 下载”  
这比“装环境 -> 跑脚本 -> 看输出”对支持场景更友好。

这意味着这条线后面如果继续演进，也最好优先保持“本地优先”的设计思路。

### 7) transcript 恢复为什么必须单独抽模块

一开始如果只为了 HTML 恢复，其实完全可以把逻辑写死在网页按钮里。

但后面很快发现：

- HTML 恢复和 Markdown / TXT 恢复，本质上都是“转成统一导入结构”
- 差别只在输入解析，不在输出格式

所以最合理的分层是：

1. 解析层：HTML / Markdown / TXT -> `{ title, messages }`
2. 组装层：`{ title, messages }` -> Chatbox 导入 JSON

这样做的好处：

- 输出结构永远只有一套
- 新增输入格式时，只要补新的解析器
- 网页和其他脚本都能复用同一份核心逻辑

这也是为什么后来会抽出单独的 transcript 转换模块，而不是把逻辑继续堆在 `app.js` 里。

---

### 8) HTML 恢复和文本恢复，本质难点不一样

这次有一个很值得记的体感：

#### HTML 恢复

更偏“结构提取”问题：

- DOM 结构是否稳定
- role 标签怎么识别
- 正文节点怎么抽

如果导出结构稳定，HTML 恢复通常比较可控。

#### Markdown / TXT 恢复

更偏“弱结构文本解析”问题：

- 角色标记写法可能非常不统一
- 装饰分隔线会干扰切段
- fenced code block 可能只是包裹正文，不是真正代码
- 导出页脚 HTML 可能混进最后一条消息

也就是说：

- HTML 的风险是模板变了
- 文本的风险是格式太自由

这两类问题不能用同一种心智来处理。

---

### 9) 这次修过的几个具体边界，后面不要忘

#### 边界 A：Markdown fenced block 被写进正文

典型模式：

````md
**user**:

```text
消息内容
```
````

如果不做特殊处理，消息正文里会残留：

- 开头的 ``` 
- 结尾的 ```

#### 边界 B：纯文本前缀不是普通 `USER:`

真实文本里可能是：

- `▶ USER:`
- `▶ ASSISTANT:`
- 带各种符号装饰的 role 行

如果 parser 只认最理想格式，就会把整篇当成一条消息。

#### 边界 C：导出页脚混入最后一条消息

Markdown 导出末尾可能有：

- 分隔线
- Chatbox 链接
- logo HTML

如果不截断，这些会被拼进最后一条 assistant 消息里。

#### 边界 D：空 fenced block 不能被当成有效正文

有些 assistant 回复本来就是空的，导出后会变成：

```text
```

```
```

这种情况下不能硬保留一条只包含 ``` 的消息文本。

这些边界都不算“大理论”，但是真实恢复工具最容易死在这种细节上。

### 10) 这条线里“能修”和“不能修”的分界

这个分界以后一定还会反复用到，值得单独写清楚。

#### 能修的

这类问题满足一个条件：  
**结构上缺失，但可以从上下文或规则稳定推断。**

例如：

- `session.id` 缺失，但 key 里有 id
- `messages` 缺失，但可以补 `[]`
- `chat-sessions-list` 缺失，但可以从 sessions 重建
- `meta.name` 缺失，但可以从 session 或首条正文推断

#### 不能真正修的

这类问题满足一个条件：  
**原始业务内容已经丢失，无法从现有结构中可靠推断。**

例如：

- 图片二进制已经不在导出数据里
- `storageKey` 指向的附件本体已丢失
- 用户原始时间戳根本不在输入文件中

对这类问题，正确做法是：

1. 提示
2. 标记边界
3. 不伪造“看起来完整”的恢复结果

这是工具可信度的关键。

### 11) 如果以后继续做，这几个方向最值得补

#### 方向 1：批量模式

当前更偏单文件处理。  
如果以后支持团队用得多，批量模式会很有价值：

- 批量检测
- 批量转换
- 统一导出结果

#### 方向 2：错误解释层

现在已经能告诉用户“哪里有问题”，但还可以更进一步：

- 这个问题为什么会影响导入
- 是否可自动修复
- 修复后可能还有什么残余风险

#### 方向 3：恢复前后 diff

如果用户能看到：

- 原文件哪里坏了
- 修复后具体改了哪些字段

会更容易建立信任。

#### 方向 4：更强的 transcript 格式适配

目前已经支持 `HTML / MD / TXT`，但后面还可能遇到：

- 其他导出模版
- 更自由的角色命名
- 混合正文 + 工具调用日志的文本

这块未来大概率还会继续长。

### 12) 这篇文档真正想给未来的自己留什么

最重要的不是“我实现了一个网页”，而是下面这几个判断：

1. **支持场景的问题，最好抽成规则，而不是只靠人工经验。**
2. **规则成熟后，应该尽快变成低门槛工具，而不是停留在命令行。**
3. **数据恢复工具最重要的是边界感，不是修得越多越好。**
4. **真实文件的脏格式，远比理想示例更能决定工具质量。**

如果以后再遇到类似“导入失败 / 数据恢复 / 历史记录救援”的工作，可以直接复用这套思路：

```text
先分层
  -> 再收敛可修规则
    -> 再做自动化工具
      -> 再补真实样本边界
        -> 最后做低门槛入口
```

这其实就是这次工作的真正方法论沉淀。
