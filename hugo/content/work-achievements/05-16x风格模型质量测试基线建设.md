## 背景与问题定义

### 1) 业务场景

模型迭代频繁，团队需要在多个候选模型间快速比较质量，并判断某版本是否发生能力退化。

### 2) 原始痛点

1. 评估标准不统一，结论高度依赖个人偏好。
2. 只看单次输出容易误判，无法识别稳定性问题。
3. 有结果无解释，难形成可执行改进建议。

### 3) 影响评估

- 决策风险：模型选型容易受主观印象影响。
- 协作风险：同一输出不同人结论差异大。
- 复盘风险：无法回答“这次好坏到底差在哪”。

---

## 我在这件事里实际做了什么

1. 我先把任务边界收紧到一个高频且可验证的 clean-MDX 场景，避免一上来做大而泛的 benchmark。
2. 我把评测输入、目标输出、评分规则、执行命令和结果文件全部固化成仓库资产，而不是只保留在对话或临时脚本里。
3. 我把评分从“通过/失败”改成“分数 + 问题类型 + 稳定性”的组合视角，这样模型好坏不仅能排序，还能解释差异来自哪里。
4. 我把同模型多次尝试归并成同一 base name，让比较标准从“单次最高分”转向“平均表现 + 波动性”。
5. 我保留了多批 model responses 与 eval JSON，保证未来回看时不仅能知道结论，还能知道当时到底拿什么输入、怎么打分、跑出了哪些输出。

---

## 目标与验收标准

### 1) 目标

1. 定义统一任务与评分规则，保证对比公平。
2. 自动化输出分数、差异量、问题类型、质量排名。
3. 引入多次运行统计，识别稳定性差异。

### 2) 验收标准

- 同一输入和目标输出可对多个模型批量运行评测。
- 结果包含分数、差异量、问题分级，而不仅是“通过/失败”。
- 支持多次尝试归并，输出平均分、最好/最差、标准差。
- 评测结果可通过脚本重复执行并复现。

---

## 约束与边界

- 约束 1：评测任务需足够聚焦，避免任务过大导致解释困难。
- 约束 2：评分必须兼顾准确性与执行成本，适配日常迭代节奏。
- 约束 3：评测不等于完整能力画像，本次聚焦文本清洗任务质量。
- 非目标：不在本阶段做全场景 benchmark，只先把“高频关键任务”做精。

---

## 核心原理与评测资产矩阵

### 1) 为什么这样设计

1. 同任务、同标准、同输入才可比较：模型评测不是“看输出印象”，而是受控实验。
2. 评分需要可解释拆解：只有总分不够，必须能分解到错误类型，才能支持后续优化。
3. 单次结果不代表真实能力：平均分 + 波动性比峰值更接近生产可靠性。
4. 评测系统要支持持续复跑：能低成本重复执行，评测结论才有长期价值。

### 2) 当前真实评测资产矩阵

| 资产类型 | 真实路径 | 当前可见证据 |
| --- | --- | --- |
| 任务说明 | `16x/clean-mdx/PROMPT.md`、`FULL_PROMPT.md` | 定义任务输入与要求 |
| 评分规则 | `16x/clean-mdx/RUBRICS.md` | 明确扣分项、加分项与多次尝试口径 |
| 基线实现 | `16x/clean-mdx/cleanMDX.ts` | 作为本地基准算法 |
| 执行引擎 | `16x/clean-mdx/test-models.ts` | 负责加载模型、评分、聚合 |
| 辅助脚本 | `16x/clean-mdx/test.ts`、`import-from-16x.ts` | 调试与导入支持 |
| 输入与期望 | `sample-input.mdx`、`expected-output.md` | 同一输入、同一期望输出 |
| 历史结果 | `evals-clean_mdx-2025-12-24.json`、`evals-clean_mdx-2025-12-25.json` | 批量运行后的真实结果落盘 |
| 模型样本 | `model-responses/`、`model-responses1/` | 保留输出文本和实现代码 |

### 3) 原理流转图（简化）

```text
统一输入与目标输出
  -> 多模型执行同任务
    -> 自动评分（分数 + 问题类型）
      -> 按 base name 聚合多次尝试
        -> 输出 avg / best / worst / sigma
          -> 留存 JSON 结果与模型样本
```

### 2) 这些落点分别说明了什么

- `RUBRICS.md` 说明：评分不是口头规则，而是明确写进文件的扣分/加分体系。
- `test-models.ts` 说明：评测不是人工对比，而是脚本化加载、评分和聚合。
- `evals-*.json` 说明：结果不是实时打印后就丢掉，而是可以归档、复盘、对比。

### 3) 一个最值得记住的工程细节

`test-models.ts` 里不是简单按文件名排序，而是先做 base name 映射，把同模型的第 1 次、第 2 次尝试聚合到一起。这一点决定了这套评测看的是稳定性，而不是偶然一次的最好表现。

## 我的关键动作

### 1) 固化任务与评分规则

- 明确任务规则：去 frontmatter、去 import、去表格/组件、展开代码块与链接、保留正文语义等。
- 建立 rubrics：内容完整性为主，结构残留和格式问题为扣分项。
- 增加“短实现/高效率”正向加分与“剩余差异”惩罚，避免单点优化刷分。

### 2) 构建自动评分引擎

- 基于字符差异、行差异做基础量化。
- 实现问题类型识别（critical / major / minor）并映射扣分影响。
- 输出每个模型的缺陷列表，便于直接定位改进方向。

### 3) 增加稳定性统计维度

- 设计同模型多次尝试归并机制（按 base name 聚合）。
- 统计平均分、最高分、最低分、标准差（sigma）。
- 排名优先看平均分和稳定性，而不是单次峰值。

### 4) 形成可执行操作面

- 提供标准、详细、单模型、评分视图等多模式命令。
- 支持导入不同模型实现，统一进入同一评测流程。
- 让评测从一次性实验变成持续可跑的工程能力。

## 难点、风险与应对

### 1) 难点

- 单任务评测容易高分，但不代表稳定可靠。
- 纯分数无法表达“错在哪”，改进路径不清晰。
- 模型输出和模型实现代码如果不一起保留，后续很难准确复盘。

### 2) 风险与应对

- 风险：单次偶然高分误导选型。  
  应对：强制引入多次运行与稳定性统计。
- 风险：评分细则过粗导致区分度不足。  
  应对：分级问题识别 + 差异惩罚组合评分。
- 风险：有结果文件但缺少上下文，后续无法重建实验。  
  应对：同时保留 prompt、rubrics、input、expected output、模型响应和 eval JSON。

### 3) 关键突破

- 从“主观比输出”升级为“规则化评测”。
- 从“看最高分”升级为“看平均分 + 波动性”。
- 从“只留结论”升级为“任务、脚本、样本、结果全链路可追溯”。

---

## 结果与影响

### 1) 短期结果

1. 形成统一的模型质量基线，日常可快速对比。
2. 输出可解释评分报告，便于快速定位缺陷类型。
3. 评测从一次性讨论变成有固定命令和结果文件的重复流程。

### 2) 中期价值

1. 模型选型讨论从经验判断转为证据驱动。
2. 版本回归可用同一评测流程识别能力波动。
3. 后续新增模型时可以直接接入既有基线，而不用重想评分口径。

### 3) 长期复用价值

1. 评分引擎可复用到其他高频任务。
2. 稳定性视角可作为模型上线前质量门槛的一部分。
3. 历史结果文件和样本库能长期支持复盘与对比分析。

## 关键代码与命令片段（基于当前真实资产改写）

```ts
function summarizeAttempts(scores: number[]) {
  const avg = scores.reduce((a, b) => a + b, 0) / scores.length;
  const variance = scores.reduce((sum, s) => sum + (s - avg) ** 2, 0) / scores.length;
  return {
    avg: Number(avg.toFixed(1)),
    best: Math.max(...scores),
    worst: Math.min(...scores),
    sigma: Number(Math.sqrt(variance).toFixed(2))
  };
}
```

## 可复用经验

1. 模型评测必须先统一任务边界，才能公平比较模型。
2. 评分体系要同时回答两个问题：好不好、差在哪。
3. 稳定性比峰值更重要，尤其在生产选型阶段。
4. 可复现脚本 + 历史结果文件，才是评测体系长期有效的核心。
