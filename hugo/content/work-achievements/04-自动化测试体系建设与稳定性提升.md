## 背景与问题定义

### 1) 业务场景

功能迭代加快后，手工回归成本持续上升。测试任务跨模块、跨端、跨环境，导致“漏测、误报、复现慢”的问题不断放大。

### 2) 原始痛点

1. 测试脚本分散，选择器与业务逻辑耦合，维护成本高。
2. 用例覆盖缺少台账，优先级管理弱，补测常凭感觉。
3. flaky 问题频发，失败原因难快速定位。
4. 本地与 CI 行为不一致，结果可信度不足。

### 3) 影响评估

- 交付风险：发版前验证不完整。
- 效率风险：排障时间高于用例编写时间。
- 资产风险：测试经验难沉淀，人员变动影响大。

---

## 我在这件事里实际做了什么

1. 我先做的不是“多写几个用例”，而是把原来耦合的脚本抽象成 `core / selectors / actions / tests` 分层，让后续维护成本能降下来。
2. 我把测试集按用途拆成冒烟、回归、实验、Electron、调试、移动端等不同执行区，不再把所有测试堆在一个目录里混跑。
3. 我把“覆盖建设”和“稳定性治理”合并考虑：一边建框架和入口，一边补等待策略、调试模式、报告落点，避免出现“覆盖看起来很多，但一跑全红”的假繁荣。
4. 我把运行入口、目录结构、故障排查文档、CI 文档都沉淀到项目内，让这个体系不是只存在于我脑子里。
5. 我把结果产物固定下来，让每次执行都有报告、有中间 JSON、有目录结构说明，后续别人接手时能直接定位到代码和产物。

## 目标与验收标准

### 1) 目标

1. 建立可扩展、可维护的分层测试框架。
2. 把核心业务路径纳入可持续回归链路。
3. 降低 flaky 干扰，提升失败定位效率。
4. 打通本地到 CI 的统一执行标准。

### 2) 验收标准

- 框架具备清晰分层：`core / selectors / actions / tests`。
- 核心场景具备冒烟+回归覆盖，并可按优先级扩展。
- 用例失败能通过统一调试策略快速定位。
- CI 产出可追溯报告并支持复盘。

---

## 约束与边界

- 约束 1：UI 迭代快，选择器稳定性天然受挑战。
- 约束 2：桌面应用自动化受启动模式和环境差异影响大。
- 约束 3：测试资源有限，必须按优先级治理覆盖范围。
- 非目标：本阶段不追求“100% 自动化覆盖”，优先保障核心链路稳定。

---

## 核心原理与结构矩阵

### 1) 为什么这样设计

1. 测试代码和业务 UI 要解耦：把选择器和动作分层，才能在 UI 变更时把影响面控制在最小范围。
2. 稳定性优先于覆盖率：不稳定的高覆盖只会制造噪音，先把核心链路跑稳，再做广度扩展。
3. 等待策略要以状态为中心：固定 sleep 只能“碰运气”，状态驱动等待才可迁移、可复现。
4. 测试治理本质是风险治理：覆盖运营应围绕风险优先级，而不是围绕用例总数。

### 2) 当前真实结构矩阵

| 层级 | 真实路径 | 当前可见证据 |
| --- | --- | --- |
| 核心层 | `playwrighttest/framework-v2/core/` | `base.ts / types.ts / cdp.ts / index.ts` |
| 动作层 | `playwrighttest/framework-v2/actions/` | `message / model / network / settings / sidebar` 5 个模块 |
| 选择器层 | `playwrighttest/framework-v2/selectors/` | `chat / model / sidebar / settings / common` 5 个模块 |
| 统一入口 | `playwrighttest/framework-v2/chatbox-actions.ts` | 对外收敛调用面 |
| 测试分区 | `playwrighttest/tests/` | `smoke / regression / experiments / electron / debug / mobile` |
| 运行配置 | `playwrighttest/playwright.smoke.config.ts`、`playwrighttest/playwright.regression.config.ts` | 区分冒烟与主回归 |
| 报告产物 | `playwrighttest/playwright-report/regression/`、`playwrighttest/tests/test-results/` | HTML 报告 + JSON 中间产物 |

### 3) 原理流转图（简化）

```text
需求变更进入测试池
  -> 映射到分层框架（selector/action/test）
    -> 进入覆盖与稳定性治理
      -> 执行回归（smoke / regression / debug）
        -> 失败分流（环境问题 vs 业务问题）
          -> 报告归档并更新台账
```

## 我的关键动作

### 1) 框架分层重构

- 把原本耦合脚本拆成核心层、选择器层、动作层、测试层。
- 将页面细节从业务步骤中剥离，降低 UI 变化引发的连锁修改。
- 建立统一入口类，减少用例重复代码。

### 2) 覆盖度台账化治理

- 建立覆盖矩阵：已覆盖、已覆盖但风险高、框架有能力但无测试、未覆盖。
- 引入优先级策略：先保核心回归，再逐步覆盖边缘能力。
- 让补测计划有依据，不再依赖临场判断。

### 3) 稳定性治理与调试能力建设

- 把固定超时等待改为状态驱动等待，减少误失败。
- 增加双模式调试策略，区分“环境问题”和“业务问题”。
- 沉淀失败定位路径：现象 -> 环境 -> 选择器 -> 业务逻辑 -> 断言。

### 4) CI 闭环建设

- 统一配置入口，支持环境变量控制关键参数。
- 打通执行、报告、归档路径，确保结果可追溯。
- 配套文档化，保证新成员可快速接入并复用。

---

## 难点、风险与应对

### 1) 难点

- UI 元素动态变化导致脆弱选择器反复失效。
- 异步行为波动导致“偶发红灯”难解释。
- 不同运行环境造成“本地过、CI 挂”的不一致。

### 2) 风险与应对

- 风险：为追求覆盖率引入大量低价值用例。  
  应对：优先级治理，先关键路径后边缘能力。
- 风险：调试链路不统一导致定位效率低。  
  应对：统一故障分层诊断流程与排查文档。
- 风险：目录分层做出来了，但执行入口仍然混乱。  
  应对：用独立 config、脚本命令和报告出口把“结构”变成“真实执行路径”。

### 3) 关键突破

- 从“脚本堆砌”升级为“框架化治理”。
- 从“跑通即完成”升级为“稳定可持续运行”。
- 从“只看有没有用例”升级为“同时看结构、覆盖、稳定性、报告链路”。

---

## 结果与影响

### 1) 短期结果

1. 核心路径自动化回归可持续执行。
2. 用例维护成本下降，新增场景接入速度提升。
3. 目录结构、运行入口、报告出口开始统一到同一套框架里。

### 2) 中期价值

1. 失败定位从随机排查变成结构化排查。
2. 发布前验证更可控，质量门禁更加稳健。
3. 冒烟、主回归、调试、实验不再互相挤占同一条执行链路。

### 3) 长期复用价值

1. 测试资产从个人经验沉淀为团队资产。
2. 框架和治理方法可迁移到其他端与模块。
3. 后续再做 RAG、CDP、移动端专项时，不需要从零搭测试基座。

```ts
// actions/message.actions.ts
export class MessageActions {
  constructor(private page: Page, private selectors: Selectors) {}

  async sendMessage(text: string) {
    await this.page.locator(this.selectors.input).fill(text);
    await this.page.locator(this.selectors.sendBtn).click();
    await this.waitUntilResponseStable();
  }
}
```

## 可复用经验

1. 自动化测试先保证“关键路径稳定”，再追求广覆盖。
2. 分层不是形式，而是维护成本控制的核心抓手。
3. flaky 治理必须组合策略：等待机制、调试模式、排障文档。
4. 覆盖治理要有台账和优先级，否则无法持续演进。
