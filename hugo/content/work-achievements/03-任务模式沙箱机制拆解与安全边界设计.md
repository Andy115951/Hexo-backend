## 背景与问题定义

### 1) 业务场景

任务执行能力覆盖命令运行、文件访问、工具调用和跨进程通信。能力强但风险也高，如果没有边界与治理，问题会从功能缺陷快速演化为安全与稳定性问题。

### 2) 原始痛点

1. 执行链路跨层次，出了问题很难快速定位。
2. 权限边界不清晰，评审时难回答“到底放开了什么”。
3. 故障处理策略零散，超时、取消、输出溢出等场景缺少统一定义。

### 3) 影响评估

- 安全风险：潜在越权与误操作风险难审计。
- 研发效率：跨层排查成本高，问题回归慢。
- 协作成本：产品、研发、安全对能力边界认知不一致。

---

## 我在这件事里实际做了什么

1. 我先把“任务执行”这件事从一个黑盒能力拆成多层职责：任务编排、权限检查、执行过程、故障收敛、升级路径。
2. 我把“是否允许”从经验判断变成显式策略，强调默认边界、显式升级、可见确认、可审计留痕。
3. 我把高风险动作和低风险动作区分开，明确哪些可以默认通过，哪些必须用户确认，哪些属于预批准但仍要讲清具体风险。
4. 我把故障场景也纳入同一模型里：初始化失败、超时、取消、输出截断，不再把它们当作零散异常分别处理。
5. 我保留了证据边界的诚实性：这篇文章引用的是本地规则与技能约束中可直接看到的材料，而不是把尚未独立沉淀成业务仓库模块的内容包装成“已有完整实现”。

---

## 目标与验收标准

### 1) 目标

1. 建立端到端执行链路分层模型。
2. 明确默认权限与升级策略，形成可审计边界。
3. 固化关键故障场景处理顺序，提升定位效率。

### 2) 验收标准

- 可用一张分层图解释任务从触发到执行的全链路。
- 可回答“可读/可写/禁止”路径规则以及升级触发条件。
- 对初始化失败、超时、取消、输出截断至少有统一处理策略。
- 新成员可按文档完成一次完整排障流程。

---

## 约束与边界

- 约束 1：默认策略必须最小权限，不以“功能可用”为唯一目标。
- 约束 2：跨平台行为存在差异，需要抽象一致接口。
- 约束 3：执行输出和上下文大小受资源约束，需可控截断。
- 非目标：不在本次引入复杂动态权限系统，优先建立清晰静态边界和升级机制。

---

## 核心原理与边界矩阵

### 1) 为什么这样设计

1. 默认拒绝 + 最小权限：执行能力越强，默认边界越要保守，先保证安全下限，再通过显式授权放开能力。
2. 能力授权必须显式可见：权限升级要可解释、可审计、可追踪，避免隐式放权造成边界漂移。
3. 生命周期状态机优先：初始化、执行、超时、取消、清理必须定义一致语义，避免状态错乱。
4. 可观测性是安全能力的一部分：没有足够日志和状态输出，安全策略就无法验证，故障也无法复盘。

### 2) 当前可见证据矩阵

| 维度 | 真实落点 | 当前可见证据 |
| --- | --- | --- |
| 规则放行机制 | `~/.codex/rules/default.rules` | 使用 `prefix_rule(pattern=..., decision="allow")` 显式放行能力 |
| 风险确认分级 | `computer-use/SKILL.md` | 明确 always confirm / pre-approval / no confirmation needed |
| 敏感数据边界 | `computer-use/SKILL.md` | 要求确认具体数据、具体目标、具体原因 |
| 文件/系统操作边界 | `computer-use/SKILL.md` | 对文件管理、系统设置、金融、医疗等高风险动作分类 |
| 运行时边界理念 | 当前本地 Codex 执行模型 | 体现为工作区写权限、越界需审批、危险动作显式升级 |

### 3) 原理流转图（简化）

```text
任务请求进入系统
  -> 权限与风险预检查
    -> 默认允许：进入执行
    -> 需确认：等待显式确认
    -> 默认拒绝：返回可解释原因
  -> 执行状态机
    -> running
      -> completed / timeout / cancelled / failed
  -> 记录状态与边界信息
```

## 我的关键动作

### 1) 架构分层与职责切分

我把执行链路拆成四层，避免“全栈黑盒”：

1. 会话与任务编排层：任务创建、状态流转、取消信号。
2. 平台抽象层：屏蔽平台差异，统一接口。
3. 主控进程层：生命周期管理、IPC 协调、执行调度。
4. 沙箱执行层：文件系统、网络、进程、输出约束。

每层都定义“输入、输出、失败语义”，让问题可以按层收敛。

### 2) 权限模型与升级路径梳理

我把权限分成三类：

1. 默认允许：低风险只读能力。
2. 受控允许：白名单路径写入、限定命令前缀。
3. 默认禁止：敏感路径、破坏性操作、高风险网络行为。

同时定义“显式升级”原则：需要升级权限时，必须走可见、可解释、可追踪流程。

### 3) 故障矩阵与恢复策略设计

我把常见异常统一到固定处理框架：

1. 初始化失败：前置检查 + 降级提示。
2. 执行超时：中断进程 + 状态回写 + 诊断信息。
3. 输出过长：截断保关键信息 + 提示获取完整方式。
4. 用户取消：优雅终止 + 资源回收 + 状态一致性保障。

### 4) 文档化与可传递性建设

- 输出“分层图 + 权限矩阵 + 故障顺序”的三件套。
- 把审计问题转成可检查清单，支持评审和复盘。
- 为新成员提供“读图即理解”的入门路径。

---

## 难点、风险与应对

### 1) 难点

- 可用性与安全性天然拉扯：限制太严难用，限制太松不安全。
- 多层协作中容易出现“每层都对但整体失败”的系统性问题。
- 这类能力很多时候先以运行时规则存在，而不是先有一套漂亮的独立模块代码。

### 2) 风险与应对

- 风险：隐式放权导致边界漂移。  
  应对：权限升级显式化、流程化。
- 风险：异常处理不统一导致状态不一致。  
  应对：统一状态机语义与恢复顺序。
- 风险：文档看起来完整，但证据无法对回。  
  应对：只引用当前能直接看到的规则文件和技能约束，不虚构不存在的实现。

### 3) 关键突破

- 把“经验规则”升级为“可审计策略”。
- 把“黑盒排障”升级为“分层定位”。
- 把“能力很强”这件事，转化成“边界可讲清、风险可确认、失败可收敛”。

---

## 结果与影响

### 1) 短期结果

1. 执行链路可解释，跨角色沟通成本显著降低。
2. 故障定位有顺序可循，排障效率提升。
3. 权限边界讨论从抽象原则变成了可映射到规则与确认分类的具体问题。

### 2) 中期价值

1. 安全评审从口头判断转为策略审计。
2. 后续功能扩展可在既有边界内推进，风险可控。
3. 新成员理解这类高风险能力时，不再只能靠口头交接。

### 3) 长期复用价值

1. 分层架构与权限模型可迁移到其他执行型能力。
2. “边界先行”的设计方式可成为团队默认工程实践。
3. 即使底层实现变化，这套边界设计方法依然能复用到新的运行时或工具系统里。

## 可复用经验

1. 高风险能力必须先定义边界，再谈功能拓展。
2. 排障要沿分层路径做证据收敛，避免跳层猜测。
3. 安全策略要可审计、可解释、可执行，三者缺一不可。
4. 复杂系统文档要面向协作，而不是只面向作者本人。
