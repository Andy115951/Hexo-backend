## 结果速览（以后回看先看这里）

- 复用了既有 Playwright 黑盒自动化，没有另起一套实验框架。
- 跑通了 `6 个 size × 2 组 × 6 轮 = 72 条回答` 的真实多轮阈值实验。
- B 组 `36` 轮里有 `29` 轮真实触发检索，检索触发率约 `80.6%`。
- 在真实小说切片实验中，`256KB` 下 Session RAG 聊天 token 下降 `62.1%`。
- `512KB` 下 Session RAG 聊天 token 下降 `50.0%`，同时主观质量最稳。
- `2MB` 暴露了一个关键反例：检索调用更多，但 token 与回答聚焦度反而变差。

一句话判断：这次工作不是只证明“新 RAG 能跑”，而是把“什么时候开始值得默认走 RAG”收敛成了有证据的策略问题。

---

## 背景与问题定义

在 Session Attachment RAG 能力迭代阶段，团队需要回答一个关键问题：

1. 新路径（Session RAG）相对旧路径（inline / 文件系统路径）到底有没有稳定收益？
2. 收益是体现在质量、时延、token 成本，还是只在某些文件大小区间成立？
3. 阈值（何时走 RAG）应该如何设定，才能兼顾质量与成本？

如果只靠人工点点测，有三个问题：

1. 结论不可复现，不同人、不同机器、不同环境容易得出不同结论。
2. 指标不完整，常常只有“感觉更快/更慢”而没有完整证据链。
3. 难以规模化，无法持续迭代跑 30~50 个 case 做横向比较。

因此，这次工作的核心不是“再写几个测试”，而是建设一条实验流水线：让 RAG 能力变化可以被持续测量、持续比较、持续复盘。

---

## 我在这件事里实际做了什么

为了把这件事从“临时验证”做成“可复用机制”，我实际做了五类工作：

1. **复用并统一实验入口**：不重写客户端自动化，直接基于既有 Playwright / framework-v2 / 启动助手，统一 A 组安装版与 B 组 dev RAG 的执行壳。
2. **补齐实验工程能力**：补上 A/B 配置层、启动模式抽象、缓存策略、强制模式切换、结果落盘、批跑脚本与报告生成脚本。
3. **补齐真实链路保护逻辑**：把“上传完成”和“索引 ready”分开处理，增加发送前等待、附件状态确认、失败回放与结构化日志，避免把 UI 偶然状态误判成产品结论。
4. **设计阈值实验样本**：基于同一段真实连续文本切出 128KB~2MB 多档文件，并配套同一组多轮问题，确保“大小变化”是主要变量，而不是内容变化。
5. **把结果收敛成策略建议**：不是只给 raw 数据，而是结合 token、时延、检索触发率和主观质量，给出 `256KB` / `512KB` 两档可执行候选，以及 `1MB+` 暂不建议默认启用的判断。

## 为什么选择复用原自动化框架

### 1) 复用比重写更稳更快

实验并不是独立产品，它依赖主链路能力（启动 app、切模型、发消息、传附件、读响应）。这些能力在既有框架里已经成熟，重写只会制造新变量。

### 2) 原框架具备实验需要的“可控性”

既有框架天然支持多启动模式和统一动作封装，适合做 A/B：

- `launch`：安装版基线验证
- `cdp`：连接已运行实例，适合调试
- `command`：拉起本地 dev + CDP 接管，适合新功能联调；当前标准命令已收敛为 `pnpm start:cdp`

### 3) 一套动作层可复用于多个实验

核心实验 spec 直接复用了 `framework-v2` 与回归启动助手：

- `ChatboxActionsV2`（统一动作入口）
- `bootstrapRegressionApp`（标准化启动路径）

这样实验脚本的关注点可以放在“对比逻辑与指标采集”，而不是 GUI 操作细节。

## 实验架构设计

## 1) A/B 分组定义

- A 组：旧路径（inline / 文件系统路径）
- B 组：新路径（session-rag）

两组共用同一套问题集、同一模型关键词、同一输出格式，保证横向对比公平。

## 2) 启动模式抽象

实验支持三种启动策略（由配置与环境变量驱动）：

1. `launch`：直接启动安装版应用
2. `cdp`：接管已启动实例
3. `command`：后台拉起 `pnpm start:cdp`，再走 CDP

补充说明：
- 当目标明确是 `chatbox-pro` 开发态验证时，默认只走 dev/CDP（`9333`），不应静默回退到安装版。

这使得“旧版安装包 vs 本地新功能分支”可以在同一实验框架里跑通。

## 3) cache 策略控制

支持 `cold` / `warm`：

- `cold`：复制运行时文件并刷新 mtime，尽量规避缓存干扰
- `warm`：直接用原始 fixture，观察缓存命中体验

阈值实验主要使用 `cold`，目的是看真实首次成本曲线。

## 4) force mode 控制

支持 `default | inline | session-rag`，可用环境变量在同一配置下强制模式切换，便于做“同样文件 + 同样问题 + 不同路径”的精准对照。

## 用例与数据设计

本次实验包含两类数据源：

1. 真实样本轮次（real rounds）  
2. 合成阈值样本（按 128KB/256KB/512KB/1MB/1.5MB/2MB 切片）

问题设计覆盖：

1. 事实定位题（看召回准确性）
2. 多文档路由题（看跨文件检索能力）
3. 多轮追问题（看会话承接与检索策略）
4. 无答案题（看保守性，防幻觉）

每题配备：

1. `mustInclude`（必须命中要点）
2. `forbidden`（禁止错误要点）
3. 备注（用于人工复盘）

这样可以把“质量”从主观印象拆成可计数指标。

### 本轮小说阈值实验实际使用的 6 个问题

为了保证不同 size 的可比性，这轮阈值实验在 6 个文件大小上都使用同一组问题：

1. T1：开场设定 / 九位参与者 / 人羊身份
2. T2：说谎者投票规则
3. T3：身份牌 / 齐夏 / 李明
4. T4：三人异常线索 / 崇圣寺三塔
5. T5：草稿纸 / 房间体积 / 54.6
6. T6：最终投票 / 制裁 / 死亡状态

这组题刻意覆盖了：开场事实、规则定位、人物信息、跨段线索、数字计算和多轮追问，方便观察不同大小下的召回稳定性与上下文污染。

## 1) 时延类

1. App 启动耗时

1. `mustIncludeHitRate`

## 执行链路与脚本化

## 1) 单次 A/B 运行

基于 `rag-ab-eval.spec.ts`，按配置自动执行 case，结果落 JSONL。

## 2) 多轮真实实验

通过 `run-rag-ab-real-rounds.sh` 批跑多轮：

1. 每轮先跑 A 组（安装版）
2. 再跑 B 组（本地 session-rag dev）
3. 输出单轮报告
4. 最后聚合多轮报告

1. 自动生成 fixtures 与 config

3. 汇总为 threshold summary

## 4) 结果产物

实验目录统一输出：

1. `rag-ab-raw-*.jsonl`（原始逐条记录）
2. `rag-ab-summary-*.md`（A/B 总结）
3. `rag-threshold-summary-*.md`（阈值扫描）
4. `rag-threshold-dev-combined-report-*.md`（客观 + 主观综合）

## 关键实验结果（基于当前已产出报告）

## 1) real-3rounds 聚合观察

在 `real-3rounds-001` 聚合结果中：

1. A/B 两组成功率都达到 100%。
2. B 组上传+索引等待显著高于 A（首轮成本明显）。
3. B 组检索调用与召回结果数更多，说明确实在走检索路径而非“伪成功”。
4. A/B `must hit rate` 都较高，但不同 case 会出现互有优劣。

结论：B 组能力是“可用且可跑通”的，但成本结构与 A 组不同，必须结合阈值策略做取舍。

## 2) threshold-main-001 观察

在 `threshold-main-001` 报告中，6 个 size 都完成 A/B 对比：

1. 128KB~2MB 全部跑通，数据完整。
2. 多个 size 下结论偏向 inline（尤其在首轮索引等待成本较高时）。
3. 随 size 变大，session-rag 的等待成本与稳定性压力同步上升。

## 3) novel-threshold-main-001 综合结论

综合客观指标与主观质量后，报告给出更可执行的策略建议：

1. `256KB` 与 `512KB` 是高价值候选区间。
2. `512KB` 偏稳健：质量稳定、token 有明显下降。
3. `256KB` 偏激进：token 节省更明显，但要持续观察波动。
4. `1MB+` 不建议直接默认：等待成本和召回偏移风险上升。
5. `2MB` 出现“调用更多但质量与成本不一定更好”的反例。

## 开发视角下最值得看的数字

如果这篇文档是给研发同学看的，我认为最值得优先关注的是下面这些数字：

1. `72` 条回答：`6 个 size × 2 组 × 6 轮`，说明这不是单点对话截图，而是完整实验面。
2. B 组检索触发率 `80.6%`：`36` 轮里有 `29` 轮真实调用了 `query_session_attachment`，说明 B 组不是“只索引不检索”的伪实验。
3. `256KB`：聊天 token 下降 `62.1%`，是最激进也最亮眼的候选区间。
4. `512KB`：聊天 token 下降 `50.0%`，同时主观质量最稳，是更适合默认值讨论的候选。
5. `2MB`：聊天 token 反而上升 `29.6%`，并出现检索偏移，这是非常重要的反例，避免我们误以为“文件越大越该走 RAG”。

### 2) 时间口径说明

- `Inline Tokens` / `RAG Tokens` 是聊天模型 UI 侧抓到的 token，用来比较真实对话成本。
- `RAG Upload+Index(s)` 包含上传、解析、chunk、embedding、index ready 和 UI 稳定等待，更接近用户首次上传到可安全发送的等待成本。
- inline 一侧的上传时间在自动化中主要是保护性等待，因此更适合拿来做“口径说明”，不适合直接作为旧路径真实上传性能曲线。

### 3) 以后回看最值得记住的代表性样本

1. **256KB T4**：inline 只答了地点，漏掉共同异常；RAG 完整回答地震、广告牌、跨省异常、云南大理。这是“RAG 不只是省 token，还可能改善定位”的最强证据。
2. **256KB T6**：inline token 高到 `230,239`，RAG 仅 `15,134`，而且这轮 B 组没有检索也能答对，说明上下文复用本身也会影响成本结构。
3. **512KB T4 / T6**：T4 回答最稳，T6 即使未检索也能保持完整，是我最后更偏向 `512KB` 而不是只盯 `256KB` 的主要原因。
4. **1.5MB T4**：虽然整体 token 还在下降，但这一轮已经开始偏向其他人物关联，说明“更大文件”开始引入检索焦点漂移。
5. **2MB T4**：RAG 明显答偏，把共同异常答成“人物交集”，这是大文件召回偏移最清楚的反例。
6. **2MB T6**：RAG 检索了 `4` 次、用了 `76,081` token，虽然答案主体还对，但成本已经失控，是“检索越多不一定越省”的直接证据。

## 这次工作的价值不是“跑出了数字”，而是“建立了机制”

## 1) 把一次性实验变成可重复流水线

后续只需替换 fixture 或 case，即可复用整套流程复跑并生成同格式报告。

## 2) 把争议从“感觉”变成“证据”

关于“该不该提高阈值”“新路径是否更优”的讨论，从主观争辩变成指标对话。

## 3) 把研发联调成本压低

通过 `command + CDP` 模式，实验可以直连本地 dev 功能分支，不需要每次打包安装再验证。

## 4) 为产品策略提供输入

阈值策略不再是拍脑袋，能够给出“默认值 + 灰度值 + 暂不推荐区间”的分层建议。

---

## 为什么这件事有工程难度

从表面看，这件事像是在“写几个实验脚本”；但真正的难度在于，它必须走真实客户端链路、真实文件处理链路和真实模型回答链路。难点主要有四类：

1. **不是 API 对比，而是 Electron 客户端黑盒对比**：只测接口很容易，但产品真正表现的是上传、索引、发送、生成、渲染这一整条链。
2. **新旧路径的运行方式天然不一致**：A 组更接近安装版，B 组更接近本地 dev RAG 功能，需要在同一套实验壳里统一。
3. **“附件可见”不等于“可安全发送”**：Session RAG 里真正重要的是索引 ready，否则会弹“文档正在索引中”，所以必须补保护逻辑。
4. **大文件问题不是简单的“更慢”**：更关键的是可能出现“检索更多但回答更偏”的反直觉情况，因此要把检索触发率、召回规模和回答质量一起看。

---

## 难点与应对

## 1) 难点：A/B 环境不一致导致结果噪音

应对：

1. 引入 `cold/warm` 策略明确实验目标
2. `cold` 模式下复制 runtime 文件并刷新 mtime
3. 输出完整日志与原始 JSONL，便于回放与复盘

## 2) 难点：RAG ready 判定复杂

应对：

1. 尝试通过 debug IPC 获取 `session-attachment-rag` 快照
2. 判断 attachment 的 index ready 状态
3. 不可用时回退到保护性等待，保证实验可持续

## 3) 难点：质量评价容易主观化

应对：

1. 结构化 `mustInclude` / `forbidden`
2. 叠加 turn 级数据统计
3. 在关键样本上补充主观评审报告，形成双证据

## 可复用方法论（给后续实验）

## 1) 先定“比较壳”，再扩“问题集”

保持统一 spec 与输出协议，后续只扩 case，不改框架主干。

## 2) 指标与结论分层

1. 先看稳定性（success）
2. 再看成本（时延/token）
3. 最后看质量（命中率 + 人工复核）

## 3) 阈值决策要看区间，不看单点

单个 size 的一次结果不代表长期最优，必须多轮聚合 + 多数据源交叉验证。

## 4) 让实验“可追责”

每个结论都能回到对应 run id、raw JSONL、summary 报告与脚本版本。
