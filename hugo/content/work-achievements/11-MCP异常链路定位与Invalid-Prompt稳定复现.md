## 背景与问题定义

在 Chatbox 的 agent / MCP 场景中，用户偶发遇到下面的错误：

```text
API Error: Error from ChatboxAI: AI_InvalidPromptError:
Invalid prompt: The messages do not match the ModelMessage[] schema.
```

这个问题有三个迷惑点：

1. 请求看起来根本没发出去，容易误判成网络或服务端问题。
2. 往往不是在工具失败当下报，而是在“下一条普通消息发送时”才报。
3. 连续报错几次之后又可能恢复正常，表现得像“偶发抽风”。

如果只停留在表面，很容易得出错误结论，比如：

- 某个模型不稳定
- 新消息内容异常
- Chatbox AI 服务偶发失败

但这些都不是根因。

---

## 我在这件事里实际做了什么

为了把这个问题从“偶发反馈”变成“工程上可处理的问题”，我做了五件事：

1. 先把错误定位到前端本地链路，而不是后端请求链路。
2. 设计了一个专门用于复现异常 transport 的本地 MCP。
3. 验证普通 MCP tool error 不够触发，必须制造 transport 崩溃级异常。
4. 把“继续发下一条消息才报错”的现象和 prompt 组装链路对应起来。
5. 进一步解释了为什么报错不会永久持续，而是会在若干轮后自行消失。

---

## 稳定复现路径

### 1) 复现工具

构造了一个本地自定义 MCP，只提供一个故意失败的工具：

- 工具名：`crash_transport`
- 行为：调用后直接 `process.exit(1)`，模拟 MCP transport / 子进程异常退出

核心作用不是返回业务错误，而是模拟“原始异常对象从工具链路泄漏出来”的场景。

### 2) 复现步骤

1. 在 Chatbox 中配置本地自定义 MCP。
2. 调用 `mcp__invalid-prompt-repro__crash_transport`。
3. 结果区会出现类似：

```json
{
  "name": "MCPClientError"
}
```

4. 在同一个会话里继续发送一条普通消息，例如“你好”。
5. 立即触发 `AI_InvalidPromptError`。

### 3) 为什么这个复现有效

关键不在于“新消息发了什么”，而在于：

- 前一轮工具失败后，历史消息里已经混入了不规范的 tool result
- 下一次发送时，前端会重新把整段历史组装成 `ModelMessage[]`
- AI SDK 在本地校验时发现 schema 不合法，于是直接报错

---

## 关键排查结论

### 1) 报错位置在前端本地

这不是后端接口拒绝请求，而是前端在真正发起请求前，调用 AI SDK 时本地校验失败。

也就是说：

- 不是网络层问题
- 不是模型服务返回的错误
- 是 prompt 组装阶段已经坏了

### 2) 真正坏的是上一轮 tool result

引发问题的不是当前新消息，而是前一轮异常 MCP 调用留下来的脏数据。

坏链路可以概括成：

```text
MCP tool 异常
  -> 原始 Error / MCPClientError 进入 tool result
  -> tool result 被写入会话历史
  -> 下一次发送时重组 ModelMessage[]
  -> AI SDK 本地校验失败
```

### 3) `{"name":"MCPClientError"}` 看起来正常，但其实不健康

它表面上像普通 JSON，但语义上代表的是内部异常对象链路泄漏，而不是一个设计良好的业务错误结果。

安全的结果应该更接近：

```json
{ "error": "repro invalid prompt bug" }
```

或者：

```json
{ "error": { "name": "MCPClientError", "message": "..." } }
```

---

## 为什么会“连续报错几次后又恢复正常”

这是这次排查里一个非常关键、也很容易误判的现象。

根因不是系统自己修复了，而是坏消息后来被裁出了上下文。

Chatbox 在发送前不会把所有历史原样带入，它会先构建上下文，并默认：

- 只保留最近 `2` 轮 tool call 相关内容
- 再按 `maxContextMessageCount` 对整体历史做裁剪

这就导致：

1. 坏掉的 tool result 还在最近上下文里时，后续几次发送会继续报错。
2. 当这轮坏消息被新轮次“挤出”最近 `2` 轮 tool call 范围后，它不再进入 prompt。
3. 于是消息又能恢复正常发送。

换句话说：

不是 bug 被修复了，而是脏上下文刚好没再被带进 prompt。

---

## 根因判断

这个问题更像是一个历史缺陷在新场景下被放大，而不是某次新改动单点引入的 bug。

原因有两层：

### 1) 旧缺陷一直存在

旧版本里，对 tool error / MCP exception 的结果规范化就不够严格，异常对象有机会原样漏进消息历史。

### 2) 新版 agent / MCP 场景更容易踩中

以前主要是：

- 联网搜索
- 文档解析
- 内部文件读取
- RAG

这些大多是内部受控工具，错误形态比较规整。

而新版 agent / MCP 扩大了以下路径：

- 本地自定义 MCP
- 第三方 MCP server
- stdio / http transport
- 多轮工具调用、失败后继续下一轮

这些场景更容易出现 transport 崩溃、子进程退出、原始异常对象泄漏，因此显著放大了老问题的暴露概率。

---

## 修复建议

### 1) MCP / 工具执行边界先做规范化

不要把 `catch` 到的原始 `Error` / `MCPClientError` 直接返回或写进历史。

应统一转成安全的普通对象或文本，例如：

```json
{
  "error": {
    "name": "MCPClientError",
    "message": "..."
  }
}
```

### 2) 组装 prompt 前再做一次兜底清洗

在把消息历史转换为 `ModelMessage[]` 前，对以下内容统一做 `sanitize`：

- tool-call input
- tool-result output

至少需要处理：

- `Error`
- `undefined`
- `Date`
- `URL`
- 二进制对象
- 循环引用

目标很明确：传给 AI SDK 的必须始终是 schema-safe 的结构。

---

## 结果与影响

### 1) 短期结果

- 获得了稳定复现路径，问题不再依赖偶发运气。
- 明确了问题归属在前端 prompt 组装链路，而不是服务端。
- 解释了“报错几次后恢复”的真实原因，避免误判。

### 2) 中期价值

- 后续排查同类 agent / MCP 问题时，可以优先检查 tool result 序列化链路。
- 团队可以把这条复现 MCP 保留为回归工具，避免修复后再次回归。

### 3) 长期复用价值

- 沉淀了一个“异常 transport 类问题”的最小复现手段。
- 沉淀了一个典型经验：前端本地 prompt 校验错误，不一定是当前消息错，先回看上一轮工具结果。

### 4) 关键经验

- “请求没发出去”不等于后端问题，AI SDK 也可能在本地先拦截。
- “下一条消息报错”不等于下一条消息有问题，常常是上一条工具结果污染了历史。
- “报错几次后恢复”不等于系统自愈，可能只是上下文裁剪把坏消息移除了。

---

## 为什么这件事值得写成成就

这类工作难点不在于“修一行代码”，而在于把一个高度偶发、跨多层链路、症状延后出现的问题，收敛成团队可以理解和复用的机制结论。

真正的价值不是只回答“怎么修”，而是把下面几件事讲清楚：

- 为什么它一直没被发现
- 为什么现在更容易出现
- 为什么不是新消息的问题
- 为什么会报几次又恢复
- 真正应该在哪一层修

这类排查会直接提升团队处理复杂 agent / MCP 问题的速度和判断准确率。
