## 背景与问题定义

### 1) 业务场景

在稳定性验证阶段，需要对多条上游链路并行做弱网注入，用于复现“偶发超时、连接中断、响应抖动”等问题，并对比修复前后行为差异。

### 2) 原始痛点

1. 弱网注入可偶尔生效，但无法稳定复现，导致问题难复盘。
2. 多链路并行场景下，单点配置常互相干扰，结果不可解释。
3. 出现失败时无法快速判断根因属于配置、网络、权限还是环境冲突。
4. 操作高度依赖个人经验，难以交接和团队复用。

### 3) 影响评估

- 复现效率低：同类问题反复人工尝试。
- 定位周期长：链路复杂导致排查顺序混乱。
- 验证可信度低：缺少统一基线与证据标准。

---

## 我在这件事里实际做了什么

1. 我把弱网注入动作拆成两层：单链路脚本负责 profile 细节，多链路脚本负责批量 up/down/profile/status，先把“能控”这件事做实。
2. 我把 profile 口径标准化到脚本里，不再允许每次现场自由调 latency/timeout/bandwidth，保证不同人执行同一档位时结果可比。
3. 我把排障顺序固定成分层流程：先看端口与进程，再看代理映射，再看 DNS，再看运行模式与权限，避免多人协作时排查路径发散。
4. 我把联调结论从“感觉生效了”改成“三联证据必须一致”，让修复前后对比和回归验收都能留下可审计证据。
5. 我把这些能力沉淀成 runbook 式操作面，而不是只停留在我自己会用的临场经验。

---

## 目标与验收标准

### 1) 目标

1. 建立多链路并行可控的弱网注入能力。
2. 形成标准档位，保证不同人执行结果一致。
3. 建立可追溯证据链，支持“复现-修复-回归”闭环。

### 2) 验收标准

- 能在 `normal / mild / flaky / harsh` 四档之间稳定切换。
- 能同时对多目标链路进行状态查询、档位切换和恢复。
- 每次联调都能留下三类证据：工具状态、连通性结果、日志轨迹。
- 出现失败时可按固定排查顺序收敛根因。

---

## 约束与边界

- 约束 1：本机网络环境和代理策略会影响链路可达性。
- 约束 2：不同运行模式（容器/宿主）存在实现差异。
- 约束 3：低端口、进程残留、DNS 路径等会产生叠加噪音。
- 非目标：本次不追求全量网络协议仿真，只聚焦核心链路弱网复现能力。

---

## 核心原理与联调矩阵

### 1) 为什么这样设计

1. 控制面与验证面分离：脚本只负责“配置与状态”，验证步骤只负责“连通性与日志”，避免把问题藏进脚本黑盒里。
2. 档位标准化优先于调参自由：能重复比“偶尔更像真实弱网”更重要。
3. 排障顺序优先于排障技巧：先判断是哪一层出问题，再进入细节操作，能显著降低误判。
4. 结论必须证据化：没有状态、连通性、日志三联闭环，就不算真正完成联调。

### 2) 弱网 profile 与控制矩阵

| 维度 | 当前真实落点 | 说明 |
| --- | --- | --- |
| 单链路控制脚本 | `scripts/toxiproxy-chaos.sh` | 管 `init / profile / status / cleanup` |
| 多链路控制脚本 | `scripts/toxiproxy-chaos-multi.sh` | 管 `up / down / profile / status` |
| 目标链路 | `deepseek / qwen / chatbox / all` | 支持单链路或并行操作 |
| 运行模式 | `native / docker` | 通过 `TOXIPROXY_MODE` 控制 |
| 标准档位 | `normal / mild / flaky / harsh` | 已固化在脚本 `apply_profile()` |
| 状态面板 | `curl .../proxies` + `status` 命令 | 用来确认代理与 toxic 是否真生效 |

### 3) 原理流转图（简化）

```text
选择目标链路与 profile
  -> 初始化 / 更新 Toxiproxy
    -> 注入 toxic
      -> 采集状态证据 + 连通性证据 + 日志证据
        -> 证据一致：判定命中
        -> 证据不一致：按固定分层顺序排障
```

## 关键样例与代码落点

### 1) 真实脚本落点

- 多链路脚本：`/Users/apple/Documents/code/other/surge-config/scripts/toxiproxy-chaos-multi.sh`
- 单链路脚本：`/Users/apple/Documents/code/other/surge-config/scripts/toxiproxy-chaos.sh`

### 2) 这两个脚本分别证明了什么

- `toxiproxy-chaos.sh` 证明：profile 不是概念，而是已经编码进脚本的真实 toxic 组合。
- `toxiproxy-chaos-multi.sh` 证明：多条上游链路可以统一 up/down/profile/status，而不是逐条手工切换。
- `status` 与 `curl /proxies` 证明：联调时能直接看到代理状态、upstream、listen、toxics，而不是只凭业务现象猜测。

### 3) 一个最典型的收敛样例

当某次“弱网档位已切成功，但业务层没有出现预期超时”时，我不会直接判断脚本失效，而是按固定顺序收敛：

1. `status all` 看代理是否真的存在。
2. `curl /proxies` 看 toxic 是否在正确 target 上。
3. 看 listen/upstream 是否对应到当前目标域名。
4. 对比 `native` 与 `docker` 模式，排除环境差异。
5. 再看 DNS/系统权限/进程残留等外围噪音。

这类收敛方式的价值，不在于某一次“修好了”，而在于不同人接手时能走同一条排障路径。

## 我的关键动作

### 1) 搭建可执行控制平面

- 把启动、下线、切档、状态查询统一到脚本入口。
- 把弱网参数抽象为标准档位，降低临场调参误差。
- 支持多目标并行操作，避免逐个链路手工切换。

### 2) 建立“链路分层排障法”

我把排障拆成固定顺序，避免盲查：

1. 端口与进程：确认无冲突、无残留。
2. 网络入口：确认监听地址与回环可用。
3. 代理配置：确认目标映射完整且无漏配。
4. DNS 路径：确认未被异常策略劫持导致假目标。
5. 运行模式：比对容器与宿主模式差异。
6. 权限边界：确认低端口与系统权限限制。

### 3) 固化“证据化验证”

每次验证必须同时满足：

1. 状态证据：代理是否处于预期档位。
2. 连通性证据：目标请求在预期扰动下是否出现可解释行为。
3. 日志证据：建立连接、注入扰动、收尾恢复完整可追踪。

### 4) 输出可复用 runbook

- 把问题-根因-动作-结论整理为标准排障记录。
- 给出“先做什么、再做什么、最后如何验收”的执行顺序。
- 形成新成员可直接跟做的操作说明。

## 难点、风险与应对

### 1) 难点

- 多因素耦合导致“看起来像网络问题，实际是环境冲突”。
- 不同模式的行为差异让一次性结论难复用。
- 业务现象有时并不直接等价于代理是否真的命中链路。

### 2) 风险与应对

- 风险：档位切换成功但并未真正命中链路。  
  应对：强制加入定向连通性校验和 `status/curl /proxies` 双重检查。
- 风险：恢复流程不完整造成后续环境污染。  
  应对：把 `down all` 与清理动作纳入标准流程。
- 风险：多人协作时各自用不同排查方式。  
  应对：固定排障顺序，先层级定位，再看具体参数。

### 3) 关键突破

- 从“经验式试错”升级到“结构化排障顺序”。
- 从“单次修好”升级到“可重复复现 + 可审计证据”。

## 结果与影响

### 1) 短期结果

1. 弱网场景从偶发可复现提升为可稳定复现。
2. 联调过程有统一入口，操作一致性显著提升。
3. 多链路并行切档、状态查询、恢复动作都有了真实脚本落点。

### 2) 中期价值

1. 问题定位不再依赖某个熟手，协作效率更高。
2. 修复验证可做前后对比，回归结论可信度更高。
3. 后续遇到“是网络还是环境”的争论时，可以直接回到证据面判断。

### 3) 长期复用价值

1. 弱网测试能力成为可持续复用的工程资产。
2. 后续同类链路问题可复用同一套方法快速收敛。
3. 这套方法也能迁移到其他代理注入、环境隔离、稳定性联调任务里。

## 可复用经验

1. 联调任务先画链路分层图，再进入排障。
2. 先验证路径正确性，再做性能或权限优化。
3. 每个弱网档位都要有 `normal` 对照基线。
4. 结论必须附证据，不做“感觉修好了”的判断。
