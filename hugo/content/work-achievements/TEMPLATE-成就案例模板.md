## 一句话成就

用一句话讲清楚你的价值闭环：  
把什么问题，从什么状态，提升到什么状态。

示例：  
“把手工回归 2 天且不可重复的流程，升级为 2 小时内可稳定执行的自动化回归链路，并形成团队可复用资产。”

## 结果速览（数字版，建议强制填写）

这一节的目标，是让读者在 1 分钟内看懂“这件事到底做成了什么”。

- 实验 / 项目规模：例如多少组样本、多少轮执行、多少条结果、多少系统路径
- 最关键数字：例如 token 下降、耗时下降、成功率提升、误报率下降
- 最终建议：例如推荐默认阈值、推荐方案、暂不建议上线区间
- 一句话判断：例如“不是只证明新方案更省，而是找到了它开始真正划算的边界”

## 我到底做了什么（建议强制填写）

这一节决定这篇文档更像“平台说明”，还是更像“个人成果案例”。建议至少回答下面四件事：

- 比较对象 / 边界定义：我具体定义了什么比较对象，哪些范围算进实验，哪些不算
- 工程能力补齐：我补了哪些脚本、埋点、等待机制、保护逻辑、结果采集能力
- 样本与实验设计：我怎么设计文件、问题、轮次、实验矩阵、对照组
- 结果收敛与决策输出：我最后给了什么结论、推荐了什么阈值 / 方案、排除了什么错误方向

### 4) 关键数字（建议至少写 3~5 个）

### 5) 为什么这件事难（建议补一段）

不要只写通用难点，要写你真正解决的工程难点。例如：

- 不是 API 对比，而是真实客户端黑盒链路
- 新旧方案启动方式不同，需要统一实验入口
- “上传完成”不等于“可安全发送”，还要区分索引 ready
- 多轮回答里不一定每轮都触发检索，需要分开统计“已索引”和“实际检索”
- 大文件下可能出现“检索更多但结果更差”的反直觉现象

### 6) 关键实验数据明细（对比 / 实验类案例建议保留）

如果这篇案例依赖实验结论，建议至少保留一张“以后不翻 raw 也能回忆起来”的摘要表。

| 维度 | 建议保留内容 |
|---|---|
| 样本规模 | 例如多少 size、多少轮、多少条回答 |
| 核心成本 | token、时延、上传 / 索引等待 |
| 质量结果 | must-hit、主观质量、关键漏点 |
| 检索行为 | 检索触发率、调用次数、代表性偏移 case |
| 关键异常 | 例如某一轮 token 异常高、某一档出现召回偏移 |

建议额外保留 3~5 个“关键样本 case”，以后回看时比只看平均数更有记忆点。
