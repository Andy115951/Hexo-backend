## 结果速览（以后回看先看这里）

这次排查最重要的结论有五条：

1. **“继续后会新发一次模型请求”本身不是 Bug。** 原流在审批/步骤暂停时已经结束；继续必须把已完成 tool call/result 回放到一个新的模型请求中。正确语义是“新请求等价于从断点续跑”，不是“保留同一条网络流”。
2. 真正的 Bug 是：续跑前包含工具历史的 assistant 消息被持久化为 `generating: true`，随后被上下文构建器当成“未完成消息”整条过滤掉；模型只剩下原始用户提示，因此合理地把任务当作第一次执行。
3. 即使绕过第一层过滤，纯工具调用、没有文本的 assistant 消息还会被 `sequenceMessages()` 当成空消息跳过；这是第二层上下文丢失。
4. 回归来自 2026-08-03 的 [#970](https://github.com/chatboxai/chatbox-pro/commit/b626068a7edb23aade154dab07bf44effeb86b3f)（`fix: make running commands cancellable and readable`）：它为了让“继续后的工具运行”可以 Stop，提前把消息标记为 `generating: true` 并写入 storage，意外破坏了续跑上下文资格。
5. 修复已在 [PR #1003](https://github.com/chatboxai/chatbox-pro/pull/1003) 实现：仅在构建续跑 prompt 的副本上解除 `generating`，保留已完成 tool calls，并修复纯工具调用消息与 `maxContextMessageCount = 0` 的序列化边界。

一句话判断：这不是提示词可通过“请从 27 继续”完全解决的问题；它是**编排层把历史从模型请求里删掉**导致的确定性回归。

## 背景与问题定义

### 1) 业务场景

Chatbox Agent Mode 为防止工具无限运行，默认在连续执行 `25` 次工具调用后暂停，向用户展示“Paused after 25 steps”的继续/停止卡片。阈值定义在：

```ts
export const MAX_TOOL_CALLS_BEFORE_CONFIRMATION = 25
```

路径：`src/shared/utils/tool-call-limit-pause.ts`。

这套机制必须同时适用于两类暂停：

1. **工具步数上限暂停**：第 26 次调用前暂停，用户点击 Continue 后应继续任务。
2. **显式审批暂停**：命令执行、文件修改、应用动作等等待用户 Approve 后应继续任务。

后者往往具有真实副作用，例如写文件、执行命令、生成图片；一旦“继续”从头开始，就不只是多打印几个数字，而可能重复执行破坏性操作。

### 2) 最小稳定复现

使用下面这个故意反直觉、但非常适合作为编排测试探针的提示词：

```text
我要测试工具调用次数。请严格按下面要求做，不要合并步骤：
对 1 到 30 这 30 个数字，每个数字单独执行一次代码，每次只输出这一个数字。
必须分成 30 次独立的工具调用，绝对不要用循环，也不要一次输出多个数字。
```

预期时间线：

```text
工具调用 1 ... 25 成功
  -> 因 25 步安全阈值暂停
  -> 用户点击 Continue
  -> 已暂停的第 26 次调用执行一次
  -> 新模型请求读取 1 ... 26 的工具历史
  -> 仅继续执行 27 ... 30
  -> 完成，共 30 次
```

实际时间线：

```text
工具调用 1 ... 25 成功
  -> 暂停
  -> 用户点击 Continue
  -> 第 26 次调用执行
  -> 新模型请求看不到前面工具历史
  -> 重新宣告“从 1 开始”
  -> 再执行 1 ... 25
  -> 再次暂停
  -> 无限循环，永远无法稳定到达 30
```

### 3) 为什么这个 case 很有价值

这个计数 case 不是业务功能本身，但它把“进度是否连续”变成了肉眼可见的证据：

- 正常：后续只出现 `27、28、29、30`。
- 异常：再次出现 `1`，无需猜测模型有没有理解“继续”。
- 低风险：打印数字没有真实副作用，适合作为首次排查与自动化回归的基线。
- 可扩展：同一结构可替换为写文件、调用 API、图片生成等高风险工具，验证“不会重复副作用”。

## 现象初判：哪些判断是对的，哪些不够

### 1) 对的判断：Continue 后确实会重新请求模型

`continuePausedToolCallWithoutSessionLock()` 在手动补执行暂停调用后，会进入：

```ts
await orchestrateGeneration(
  sessionId,
  { ...message, generating: true },
  { operationType: 'regenerate', appendToMessage: true, externalAbortSignal: controller.signal }
)
```

路径：`src/renderer/stores/session/orchestration.ts`。

所以用户看到“继续后像开了一次新请求”是事实。

### 2) 不够的判断：新请求不等于必然从头开始

最初很容易把问题归因成“模型重新发请求，所以会忘记”。这不准确：大模型工具调用的标准多轮流程本来就是“工具结果回来后，再发下一轮模型请求”。关键不是请求对象是否相同，而是**新请求的 `coreMessages` 是否保留了前序 assistant tool call 与 tool result**。

代码也有表面上的保护意图：

```ts
preserveLastPromptMessageToolCalls: Boolean(options?.appendToMessage)
```

`appendToMessage: true` 会要求 `prepareAgentGenerationHarness()` 保留上一条 assistant 消息中的工具历史。因此，仅从这一行不能下结论说历史一定没带上。

### 3) 最终判断

真正需要回答的问题是：**从点击 Continue 到 `model.chatStream(coreMessages)` 之间，这条 resumed assistant message 是否还在 `coreMessages` 内？**

这把排查从“模型行为猜测”收敛为可验证的数据流问题。

## 端到端调用链复盘

### 1) 初始生成与第 25 步限制

`orchestrateGeneration()` 为每轮模型流包装工具：

```ts
chatOptions.tools = withToolCallLimitPause(tools as ToolSet, MAX_TOOL_CALLS_BEFORE_CONFIRMATION)
```

`withToolCallLimitPause()` 的计数器存在于本次 generation 的闭包中：

```ts
let toolCallsSinceConfirmation = 0

if (toolCallsSinceConfirmation >= maxToolCalls) {
  throw new ToolCallLimitPausedError(toolCallId, toolName, maxToolCalls)
}
```

第 26 次工具调用会抛出 `ToolCallLimitPausedError`。编排层捕获后，不把它当普通失败，而是把目标 assistant 消息保存成：

```text
finishReason: tool-call-paused
工具 part: state = paused
pauseReason: tool_call_limit
```

这个暂停是合理的：旧模型流已无法继续读取用户点击 Continue 的事件，必须通过下一阶段恢复。

### 2) 用户点击 Continue 后发生什么

继续逻辑大致分为：

```text
读取 session 与暂停消息
  -> 找到暂停 tool call / 同批次调用
  -> 重新执行被暂停工具
  -> 将工具结果写回原 assistant 消息
  -> 触发 appendToMessage 续跑 generation
```

这里有一个非常重要的产品语义：

- “继续”不是重试整个用户消息；
- “继续”也不是只补执行一个工具后结束；
- 它应把**原 assistant 消息中的已完成工具调用 + 新补出的工具结果**作为 history，再让模型规划剩余步骤。

### 3) 模型上下文的关键构造链

续跑 generation 的关键数据流为：

```text
orchestrateGeneration(... appendToMessage: true)
  -> targetMsgIx + 1
  -> prepareAgentGenerationHarness(... preserveLastPromptMessageToolCalls: true)
  -> messagesForPrompt
  -> buildContext(...)
  -> sequenceMessages(...)
  -> convertToModelMessages(...)
  -> model.chatStream(coreMessages)
```

排查时不能只看 `orchestrateGeneration` 是否被调用，也不能只看 UI 上工具卡片是否还显示；必须沿着这个链确认 assistant tool-call message 在每一层都存在。

## 根因：两层过滤叠加，模型只剩原始用户提示

### 第一层：`generating: true` 让 resumed message 失去上下文资格

上下文构建器会先过滤未完成消息：

```ts
export function isContextEligibleMessage(message: Message): boolean {
  return !message.generating && !message.isForkMarker
}
```

路径：`src/shared/context/message-eligibility.ts`。

问题恰好出在继续流程的生命周期状态：#970 为了让用户能在“批准后工具实际仍在执行”的阶段点击 Stop，将 resumed message 改为：

```ts
message = {
  ...updateToolCallParts(...),
  generating: true,
  cancel: (stoppedAt = Date.now()) => controller.abort(stoppedAt),
}
await modifyMessage(sessionId, message, false)
```

这一步把 `generating: true` **持久化**了。随后 `orchestrateGeneration()` 获取 session 快照并调用 `buildContext()`；这条本应承载 1～26 工具历史的 assistant 消息被 `isContextEligibleMessage` 整条过滤。

注意顺序：`preserveLastPromptMessageToolCalls` 的作用是在 `buildContext()` 后续的 tool-call 清理阶段保留指定消息；它不能把已经在 completed-message 过滤阶段消失的消息找回来。因此“已经有 preserve 参数”为何仍无效，就在这里。

### 第二层：纯工具调用 assistant message 被误判为空

即使第一层被绕过，计数测试仍有第二个陷阱。`sequenceMessages()` 原本使用：

```ts
isEmptyMessage(message)
```

而它主要看文本、图片、附件和链接。一个只包含如下内容的 assistant message：

```ts
{
  type: 'tool-call',
  state: 'result',
  toolName: 'code_execution',
  result: { stdout: '26' },
}
```

没有可显示文本，会被当成“空消息”跳过。这样即便 `buildContext()` 保留了该消息，进入模型请求前仍会丢失工具调用与工具结果。

### 第三层边界：上下文条数设为 0 时，首条 assistant 会被引用化

Codex 首轮 review 又发现一个边界：当 `maxContextMessageCount = 0`，上下文可能只剩 resumed assistant message。原有的“首条 assistant 前没有 user message”兼容逻辑会把它压成 `> 引用文本`，工具 part 再次被扁平化丢失。

这说明“工具历史存在于 Message 对象”还不够；**每一个消息变换函数都必须知道 tool call 是模型协议内容，不能按 UI 文本处理。**

## 回归从哪里引入：提交级归因

### 1) 不是 25 步功能新引入的问题

25 步暂停和 `appendToMessage` 续跑在 Agent Mode 早期就已存在。历史上，工具历史保留还专门做过加强：

- `571d78496`（2026-06-02）：初始 Agent Mode / 25 步暂停与续跑路径。
- `5393a07d8`（2026-06-02）：增加 `preserveLastPromptMessageToolCalls`，用于重试/续跑时保留最近工具历史。

因此“续跑要新请求”是既有设计，不能把它误认成最近回归。

### 2) 真正引入回归的提交

回归由 [#970 / `b626068a7`](https://github.com/chatboxai/chatbox-pro/commit/b626068a7edb23aade154dab07bf44effeb86b3f) 引入，提交标题为：

```text
fix: make running commands cancellable and readable
```

该改动的原始目标是正确的：让暂停后的执行阶段可以响应 Stop，取消正在运行的 code execution / user exec，并在 handoff 中传递 AbortSignal。

但它把下面的状态变化提前了：

| 版本 | `continuePausedToolCall` 写入 storage 时的状态 | 对上下文的结果 |
| --- | --- | --- |
| #970 之前 | 工具 part 可为 `call`，但外层 message 尚未持久化为 `generating: true` | `buildContext()` 仍把该 assistant message 视为完成历史 |
| #970 之后 | 开始恢复工具前立即持久化 `generating: true` 和 `cancel` | `buildContext()` 直接丢弃整条 assistant message |

根因不是“取消能力不该做”，而是复用了一个语义过宽的状态位：`generating` 同时表达了 UI 正在执行、可取消状态和“不能作为模型历史”三种含义。#970 满足了前两种需要，却意外改变了第三种。

### 3) 为什么这个回归会稳定出现

这是确定性状态机问题，不是模型采样偶发：

```text
continue 设置并持久化 generating=true
  -> buildContext 过滤 generating=true
  -> 续跑 history 消失
  -> 模型只有原用户请求
  -> 对“从 1 到 30”重新规划
```

所以同一模型、同一提示词、同一会话路径下会重复出现；模型只是对错误输入做了可预期反应。

## 修复方案：PR #1003 做了什么

PR：[fix: keep resumed tool-call context when continuing a paused generation](https://github.com/chatboxai/chatbox-pro/pull/1003)

PR 共分为三个提交，分别处理核心回归、审查发现的上下文极端边界，以及崩溃残留消息自愈：

| 提交 | 解决的问题 |
| --- | --- |
| `d6f3d6000` | 恢复 generation 的 resumed message 虽然 UI 仍是 `generating`，但在构建 prompt 时以 `generating: false` 副本参与 `buildContext()`；同时让已完成 tool call 不再被 `sequenceMessages()` 视为空 |
| `93f4ac9b5` | 当上下文裁剪使 tool-only assistant 成为第一条非 system 消息时，禁止把它引用文本化；改为补 `OK.` user 占位并保留原工具协议消息 |
| `397331fdb` | 处理崩溃/强退/刷新后持久化残留的 `generating: true` 消息，避免它永久转圈并永久被后续上下文过滤 |

### 1) 核心补丁：只为 prompt 修正生命周期视图

修复不直接把真实消息状态强行改为 completed，而是在 agent harness 内为 prompt 构造副本：

```ts
const messagesForPrompt = (await refreshSessionAttachmentStatuses(messages.slice(0, targetMsgIx))).map((message) =>
  message.id === resumedMessage?.id && message.generating ? { ...message, generating: false } : message
)
```

这样保留两个必要语义：

- UI 与取消逻辑仍可看到真实的 `generating: true`；
- 本次 follow-up 模型请求可以把已完成 tool results 当作历史发送。

这是比“在继续前把 message 改成 `generating: false`”更安全的修复：它不破坏 Stop、计时、状态展示与 generation 生命周期，只改变 prompt 的数据视图。

### 2) 协议级空消息判定：UI 空不等于模型空

PR 新增 `hasCompletedToolCalls()` 与 `isEmptyForModelRequest()`：

```ts
function isEmptyForModelRequest(message: Message): boolean {
  return !hasCompletedToolCalls(message) && isEmptyMessage(message)
}
```

关键思想是：

- 对 UI 文本或 token 统计而言，工具调用可以没有可见文字；
- 对模型协议而言，已完成的 tool call/result 是必须保留的结构化内容；
- 不能继续用“显示文本是否为空”替代“模型请求是否为空”。

### 3) 第一条 assistant 的协议序列修复

模型协议要求 tool result 前有对应的 assistant tool call，通常还要求 assistant 前有 user turn。对只剩 tool-only assistant 的上下文，修复采取：

```text
user: "OK."
assistant: tool-call
tool: tool-result
```

而不是把 assistant 内容变为引用文字。前者保留协议结构，后者会不可逆地丢失 `toolCallId`、`toolName`、参数和结果。

### 4) 附带修复：重启后的残留 generating 消息

流式消息会定时持久化。如果应用崩溃、强退或 renderer reload，storage 中可能留下：

```text
generating: true
tool part: call
```

旧逻辑会让它在 UI 上永久转圈，也会因同一 completed-message 过滤规则永久不进入后续模型上下文。

PR 在 session 反序列化入口调用 `finalizeStaleGeneratingMessage()`：启动前已持久化的 generating message 被终态化；未完成 `call` 转为可重试 error，`paused` 审批卡保留。

这部分与 25 步回归共享“`generating` 消息不可进入上下文”的机制，但属于更广的稳定性补强，不是本次主 Bug 的必要修复。

## 修复审查结论与边界

### 1) 已确认覆盖的主路径

- 25 步工具调用上限暂停 → Continue → 从第 26 步继续。
- `user_exec` 命令审批 → Approve → 保留已有工具 history。
- 文件修改审批与 app action 审批的同类恢复路径。
- 纯 `code_execution`、没有 assistant 文本的工具历史。
- `maxContextMessageCount = 0` 时的首条 tool-only assistant。
- 崩溃/刷新导致的 stale generating message。

### 2) Codex review 发现并已修复的 P2

首个版本只修复“工具消息不再被判空”。审查发现：在 `maxContextMessageCount = 0` 时，tool-only assistant 即使留下，仍可能走“首条 assistant 引用化”分支而损失工具 part。第二个提交 `93f4ac9b5` 已对该分支补齐测试和修复。

GitHub review thread 当时仍显示 unresolved，但不是因为问题仍在；后续提交已经覆盖该意见。合并前应把线程手动 Resolve，避免给后续维护者留下“未处理”的误导。

### 3) 评估过但不作为当前阻塞项的风险

`finalizeStaleGeneratingMessage()` 以 renderer module boot 时间判断消息是否残留。在网页端多个标签页共享同一份本地数据、且其中一个标签页仍在运行时，后打开页面理论上可能把前一页面的活跃生成误判为 stale。

本次不作为阻塞项的原因：

1. Web 多标签页本身不提供实时会话同步；通常需刷新才读取到另一页数据。
2. 主要使用场景是单窗口 Electron，真实风险较低。
3. 该能力属于附带自愈，不应阻塞已经明确修复主回归的 PR。

但以后若引入跨标签页同步、多窗口共享会话或后台 generation ownership，应把“谁拥有活跃 generation”做成显式状态/lease，而不是只依赖时间戳。

### 4) 未把“模型重新发请求”当作缺陷

不能把修复目标写成“Continue 后禁止产生新请求”。那会误导后续实现：旧流已经被暂停异常收敛，最正确的方式就是发起携带完整工具历史的 follow-up request。验收目标应该是：

```text
新请求存在，但它看到的工具历史完整；
因此只推进未完成步骤，不重做已完成步骤。
```

## 验证策略与回归清单

### 1) 单元测试（PR 已补）

## 以后排查类似问题的固定方法

### 1) 先拆成三个层次，不要一上来怪模型

```text
用户可见现象
  -> 编排生命周期（暂停、继续、取消、重试）
    -> 模型请求内容（最终 coreMessages）
```

对于“模型为什么重做/忘记/不继续”类问题，优先验证第三层。模型不能使用根本没有发给它的历史。

### 2) 每次状态位改动都问三个问题

以 `generating` 为例，任何新增/提前设置都必须检查：

1. 它是否影响 UI？例如 loading、Stop 按钮、计时器。
2. 它是否影响持久化与恢复？例如崩溃后如何终态化。
3. 它是否影响上下文 eligibility？例如是否被 `buildContext()` 过滤。

同一个字段承担多种职责时，必须为不同消费者定义不同视图，不能默认“状态正确就不会影响其他层”。

### 3) 区分 UI 空消息和模型协议空消息

以下内容对 UI 可以没有文本，但对模型绝不能丢：

- tool call
- tool result
- reasoning（取决于 provider）
- provider metadata / signature
- 结构化附件或 tool result blob 引用

任何 `isEmptyMessage`、合并消息、引用消息、裁剪 history 的重构，都应增加 tool-only message 测试。

### 4) 工具暂停/审批的正确不变量

以后评审这类代码时，可以直接用以下不变量检查：

```text
暂停前已经完成的工具调用：后续请求必须可见。
继续时刚完成的工具调用：后续请求必须可见。
仍在等待审批的调用：不能被误当成成功结果发送。
继续后的新模型请求：只能推进未完成工作，不应隐式重跑已完成副作用。
```

### 5) 需要抓取的最小证据

如果再次出现“Continue 后从头来”：

1. 保存暂停前后的 `Message.contentParts`（注意 `state`、`generating`、`pauseReason`）。
2. 打印/记录 `promptMsgs`。
3. 打印/记录传入 provider 的 `coreMessages`，重点确认 tool call/result 是否存在。
4. 确认 `maxContextMessageCount`、压缩点、分支/线程上下文。
5. 再看模型输出；不要先从模型输出反推根因。

## 产出物与复盘价值

### 1) 这次实际沉淀了什么

1. 一个可以稳定暴露“工具续跑是否连续”的 1～30 调用测试提示词。
2. 一条从用户现象到 `coreMessages` 的完整排查链路。
3. 一次提交级回归归因：明确不是 #976 的 25-step 开关 UI，也不是模型提示词变化，而是 #970 的 lifecycle 持久化变化。
4. 一个关于“同一状态字段影响 UI、取消、存储、上下文”的复盘案例。
5. 一组适用于所有 Agent 审批/暂停/重试功能的回归不变量与测试矩阵。

### 2) 这件事为什么值得长期记住

这个 Bug 很容易被描述成“AI 又不听话了”，然后通过加强提示词暂时掩盖。真正的工程教训是：

> 当模型没有按预期使用历史时，先证明历史确实进了模型请求；不要把编排层的数据丢失误判为模型能力问题。

它也说明了：取消能力、审批能力、上下文压缩和 tool protocol 不是彼此独立的模块。一个看似只改 UI 状态与 AbortSignal 的修复，可能通过 `generating` 这个共享字段，影响所有后续 LLM 请求的 history。

### 3) 未来 30 秒复述版本

> Chatbox 的 Agent 工具调用默认 25 步暂停。之前点击 Continue 后会重新发模型请求，这是设计使然；但 #970 为了支持取消，把承载工具历史的 assistant 消息提前持久化为 generating。上下文构建会过滤 generating 消息，于是新请求没有 1～26 的 tool history，只能从原始用户提示重新开始。#1003 在 prompt 视图中保留 resumed message，同时修了纯 tool-call 消息被当空消息以及零历史裁剪时被引用化的问题。这个案例提醒我们：续跑问题先看最终 coreMessages，而不是先怪模型。
