## 我主要学到的：长程 Agent 应该怎样测

传统 ChatAgent 更接近 `Query → Answer`：重点是回答是否正确、是否好用。

长程 Agent 面对的是复杂任务：它需要拆分步骤，多次调用 Tool 或 Skill，读取中间结果后调整策略，还可能生成文件或改变环境状态。因此评测单元应升级为：

```text
Prompt + Expected Behavior + Trace
```

- `Prompt`：用户要完成什么任务；
- `Expected Behavior`：允许怎样做、必须做到什么、哪些行为禁止；
- `Trace`：实际执行过程，包括规划、工具调用、中间状态、审批、产物和最终回复。

评测不再只问“答案对不对”，而是同时回答：任务有没有完成、过程是否合理、成本是否可接受、有没有安全风险。

---

## 长程 Agent 的四层评测维度

| 维度 | 要回答的问题 | Chatbox 中的例子 |
| --- | --- | --- |
| 结果 | 任务和产物是否真实可用 | RAG 答案是否准确；PPT 是否确实生成、可打开、内容完整 |
| 过程 | 执行路径是否合理、稳定、可复现 | 是否调用了正确的检索/代码/文件工具；是否出现无效循环 |
| 效率 | 时间、Token、工具调用是否在可接受范围 | 首 Token 延迟、总耗时、Token、工具调用次数 |
| 风险 | 是否越权、误操作或虚假宣称成功 | 权限审批、写文件范围、工具失败后不应声称“已完成” |

这里的关键变化是：**最终答案相同，不代表工程质量相同。** 一个 Agent 即使偶然答对，也可能经过大量无效尝试、调用错误工具或产生不可接受的成本；这些问题只能通过 Trace 观测发现。

---

## 对评测设计的启发

### 1. 从模糊评分改为可判定 Rubric

不要只让人或模型给“完成得好不好”打 0~10 分，而应把标准拆成更具体的 `pass / fail / unknown`：

- 是否使用了规定或必要的工具；
- 是否完成了目标文件的实际写入；
- 是否引用了允许的数据来源；
- 是否超过最大搜索或工具调用次数；
- 在没有证据时是否明确说明“无法确认”。

规则化部分优先自动评测；开放质量则由 AI Judge 辅助，并用少量人工金标样本校准，避免“机器给分但没人知道准不准”。

### 2. 评测集来自 Good Case 与 Bad Case

评测集不是一次性设计完的。应先覆盖高频核心任务，再把线上失败、投诉、偶发异常沉淀为 Bad Case，把高质量完成路径沉淀为 Good Case，持续回归。

### 3. 评测需要进入研发闭环

长程 Agent 的评测最终应服务于发布决策：低成本确定性用例可进入 PR 回归；真实模型、多轮任务和高风险用例可进入每日或发布前评测；结果异常时应能回放 Trace 并定位到模型、工具、环境或策略。

## 与当前 Chatbox 评测的对应关系

当前项目已有可复用基础：

- Session Attachment RAG A/B 实验已覆盖事实定位、无答案、多文件路由和多轮追问，并记录命中、禁词、检索、耗时和 Token。
- 工作模式实验已记录工具调用、首 Token 延迟、总耗时、Token、审批次数和 PPT 产物路径。

后续可在这些能力上统一 Task Schema，并补足两项关键判断：

1. **结果质量**：不能只判断“文件存在”或“关键词出现”，还需校验内容、来源、可打开性和无答案时的保守回答。
2. **轨迹与安全**：不能把 Full Access / 自动批准视为安全通过；需要独立验证权限边界、单项审批、失败恢复和“不得虚报完成”。

---

## 后续落地清单

1. 为 RAG、联网、代码执行、文件生成、权限审批统一定义 `Task + Expected Behavior + Rubric + Risk Level`。
2. 把现有采集的 Trace 转换为可回放、可归因的任务结果，而不只用于查看日志。
3. 建立 P0 确定性回归、每日真实模型评测、发布前长程任务评测三层执行策略。
4. 用版本基线和阈值输出“是否可发布”的结论，而不只做模型排名。

---

## 可复用经验

1. 长程 Agent 评测的最小单位不是“问题和答案”，而是“任务、预期行为与执行轨迹”。
2. 先让高频核心任务形成可运行闭环，再逐步扩充指标与样本；Bad Case 往往比普通样本更有价值。
3. 观测不是附属日志，而是定位、归因、回归和持续优化的基础设施。
