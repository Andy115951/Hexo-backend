# **背景**

在日常测试工作里，真正容易消耗大量精力的，往往不是“不会测”，而是要先花不少时间理解一次代码变更到底改了什么、为什么改、改前和改后分别是什么状态，以及这些变化会影响哪些测试范围和相关功能。

很多时候，改动涉及到的完整逻辑并不会直接体现在需求描述里，而是需要通过查看代码、对比实现前后、梳理调用链路和状态流转，才能真正看清楚。也正因为这样，测试设计里最容易遗漏的，往往不是显性的功能点，而是代码逻辑层面的边界、异常路径、兼容处理和潜在漏洞风险。

围绕这个过程，常见的问题通常有这几类：

1. 面对一个 `commit` 或 `PR`，需要先花时间梳理改动点、影响面、上下游关联和前后差异。
2. 很多关键逻辑只能通过代码理解，缺少统一规范时，代码逻辑层面的漏洞和风险点很容易漏掉。
3. 需求、边界、内部机制这些隐性约定没有沉淀下来，导致 AI 生成结果经常“看起来完整，实际覆盖却不稳定”。

如果这些问题没有被结构化，AI 很难稳定参与代码变更分析和测试设计。

这篇文档的目标，就是把当前已经沉淀好的测试设计方法和 skill 整理成一套可以直接复用的落地方案。

# **整体方案**

在测试设计这件事上，我们当前已经不是“直接让 AI 写 case”，而是采用两阶段流程：

1. `step1`：测试建模，不写具体用例
2. `step2`：把建模结果转成结构化用例表

对应的核心思路是：

1. 先统一测试设计口径，再追求生成效率。
2. 先让 AI 按既定方法理解代码变更逻辑，尽量完整覆盖改动范围、关联功能和潜在影响，再输出结构化结果。
3. 把查看代码、梳理逻辑、识别漏洞风险这类隐性分析过程沉淀成规范。
4. 把所有隐性经验沉淀成 skill，而不是停留在口头约定里。

# **测试用例文档生成方法**

## **两阶段流程**

测试用例文档不是直接让 AI “生成 case”，而是强制走两阶段：

1. `step1`：测试建模，不写具体用例
2. `step2`：把建模结果转成结构化用例表

这样做的原因是：

1. 先暴露风险，再决定测什么。
2. 避免一上来直接写 case，只盯住改动点本身，导致关联功能、上下游影响、边界、状态、并发、补偿等高风险维度漏掉。
3. 让评审对象从“零散 case”变成“有结构的设计结果”。

## **step1 的新版规则**

`step1` 当前已经升级，不再是单纯的“万能建模模板”，而是先做文档类型判定：

1. 默认只选一种文档类型：`功能 E2E` 或 `内部机制/升级回归`
2. 不默认把两种视角混写在一份文档里
3. 只有明确要求“两套都要”时，才拆成两份文档
4. 输出文档开头必须显式声明文档类型

这条规则很重要，因为它直接影响后续评审效率和文档可复用性。

## **step2 的作用**

`step2` 的职责不是重新分析需求，而是承接 `step1` 的结果，输出结构化表格用例。

常见产物包括：

1. Given / When / Then 用例表
2. P0 / P1 / P2 优先级分层
3. 风险类型标注
4. 后续专项回归与补测输入基线

# **Skill 是什么**

可以把 skill 理解成“给 AI 用的操作手册”。

它和普通文档的区别在于：

1. 普通文档是给人看的
2. skill 是给 AI 和人一起用的

在当前这套方案里，测试设计相关 skill 承担了三件事：

1. 固化方法论
2. 约束 AI 输出风格
3. 降低复用门槛

## **好的 Skill 应该是什么样的**

在继续往下看具体方案之前，也可以先回到一个更基础的问题：好的 skill 应该是什么样的。

这个问题并不只关心“能不能用”，还会进一步涉及：

1. 是否能够稳定承载一套方法
2. 是否能够让 AI 在明确边界内工作
3. 是否能够在不同场景下保持输出质量
4. 是否方便复用、维护和持续迭代

# **安装与同步**

## **Skill 目录**

当前本机环境中，主要有两个入口：

1. Codex 全局目录：`~/.codex/skills/`
2. Claude Code 全局目录：`~/.claude/skills/`

## **同步 step1 / step2 skill**

```bash
mkdir -p ~/.claude/skills/test-case-step1-markdown
mkdir -p ~/.claude/skills/test-case-step2-table

cp ~/.codex/skills/test-case-step1-markdown/SKILL.md \
   ~/.claude/skills/test-case-step1-markdown/SKILL.md

cp ~/.codex/skills/test-case-step2-table/SKILL.md \
   ~/.claude/skills/test-case-step2-table/SKILL.md
```

## **同步后校验**

```bash
cmp -s ~/.codex/skills/test-case-step1-markdown/SKILL.md \
      ~/.claude/skills/test-case-step1-markdown/SKILL.md
echo "step1_same=$?"

cmp -s ~/.codex/skills/test-case-step2-table/SKILL.md \
      ~/.claude/skills/test-case-step2-table/SKILL.md
echo "step2_same=$?"
```

返回 `0` 表示内容一致。

# **如何使用：测试用例文档**

## **输入建议**

在实际使用中，最常见的输入并不是一份完整需求文档，而是一次具体代码变更。最推荐的输入方式是：

1. `commit id`
2. `PR` 链接或变更说明
3. 受影响的模块、目录或关键文件
4. 这次变更更偏 `功能 E2E` 还是 `内部机制 / 升级回归`
5. 如果已经识别出相关功能、上下游模块或兼容性影响，也建议一并说明
6. 如果有额外背景，再补充需求说明、边界或风险关注点

也就是说，`需求 / 边界 / 约束` 不是必填前置材料，而是补充信息。真正的主输入通常是代码变更本身。

## **推荐流程**

1. 先跑 `step1`，产出建模文档
2. 检查文档类型是否正确
3. 再跑 `step2`，产出结构化用例表
4. 按 P0 / P1 / P2 做评审与排期

## **统一输出目录**

建议统一落到：

```bash
tests/test-case-docs/
```

当前项目里已经有真实产物可以参考，包括：

1. `chatbox-auto-updater-internal-step1.md`
2. `chatbox-auto-updater-internal-step2.md`
3. `chatbox-session-meta-storage-internal-step1.md`
4. `chatbox-session-meta-storage-internal-step2.md`

其中 `chatbox-session-meta-storage-internal-step2.md` 已经产出 `36` 条结构化测试用例，可以作为复杂升级回归场景的参考样例。

# **执行规范**

## **评审门禁**

建议统一三条门禁：

1. 没有 `step1` 文档，不进入 `step2`
2. `step1` 文档类型未声明清楚，不进入评审
3. 没有 `step2` 用例表，不进入用例评审与排期

## **版本管理**

skill 不是“一次写完永远不动”，建议维护：

1. skill 版本
2. 更新日志
3. 同步记录

## **复盘机制**

每次线上问题补测，建议固定问三件事：

1. `step1` 哪个风险维度漏了
2. `step2` 哪条用例定义不清
3. skill 是否需要补规则或补样例

# **常见误区**

## **误区 1：跳过 step1 直接写 case**

这样最容易导致：

1. 边界漏测
2. 内部机制和用户链路混写
3. 评审对象不清晰

## **误区 2：把 AI 当成自由生成器**

如果没有 skill 约束，AI 很容易产出“不符合既定方法”的测试文档。

## **误区 3：只在个人本地更新**

如果 skill 只更新个人副本，不同步主要使用入口，最终还是会回到“各写各的”状态。

# **推荐最小落地包**

如果希望这套方案可以被快速复用，建议至少提供这几样东西：

1. `step1` skill
2. `step2` skill
3. 一份标准输入示例（`commit id / PR / diff`）
4. 一份真实 step1 / step2 输出样例

# **总结**

AI 的真正价值，不是“帮我们少敲几行字”，而是把测试设计从“个人经验”升级为“统一流程”。

只要把方法、skill、目录、口径和门禁统一下来，AI 就不再只是一个聊天工具，而会变成一套可复用、可演进、可持续沉淀的测试生产力体系。

自动化代码生成与 CDP 元素定位，会在后续单独整理成另一篇知识库文档，不在本文展开。
