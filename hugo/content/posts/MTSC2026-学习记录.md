## 一、货拉拉《UI 自动化新范式：从人工驱动到 AI 驱动闭环》

- **讲师**：胡嘉椿（货拉拉 资深测试工程师，负责移动端测试效能，探索 LLM 在自动化测试落地，主张"AI+工程化"双轮驱动）
- **场景**：移动端 App UI 自动化（Android / iOS / HarmonyOS / 小程序），基于货拉拉自研的"悟空平台 + MTC DSL"脚本体系
- **一句话主旨**：把 UI 自动化从"人写脚本 + 人修脚本"的死循环，重构为"AI 生成脚本 → AI 执行 → 失败 AI 自愈 → 脚本自动更新 → 资产沉淀反哺"的全链路闭环飞轮。

### 1. 背景与痛点（PART 01）

传统 UI 自动化两端都痛：

- **生产端之痛**：人工写脚本门槛高、效率低、质量参差；新业务单场景需"人天级"产出；无法快速规模化，自动化覆盖率长期遇瓶颈。三种生产模式耗时对比：
  - 手写 UI 代码：生成 1~2h + 调试 1~2h
  - 封装 UI 模式：生成 30min~1h + 调试 30min~1h
  - UI 录制模式：生成 1~5min + 调试 30min~1h
- **维护端之痛**：单周迭代节奏下 UI 频繁微调（文案变更、ID 重构、布局调整），存量脚本 18000+，每周约 10% 维护量。一笔账：1800 条失效脚本 × 30 分钟/条 = 900 小时 ≈ 112 人天投入。维护成为"永远填不满的沙漏"。
- **失效诱因四类**：弹窗突袭、文案变更、元素变更、网络超时。人工维护链路长（排查失败原因 → 装包复现 → N 次修改调试 → 人工更新脚本），高成本 + 强滞后。

### 2. AI 脚本自愈（PART 02）—— 解决存量脚本稳定性

**目标**：解决存量脚本稳定性，减少人工维护依赖，让脚本自主介入和迭代。

#### 2.1 三层自愈框架
- **能力层**：四大核心能力 = 弹窗智能处理、文本自愈、元素自愈、智能等待
- **数据层**：
  - 多模态数据基线：APP 信息、用例步骤、设备截图、OCR 快照、DOM 树&结构清洗、控件画像
  - 用例库管理：脚本映射、自愈标记、用例同步&更新、效果评估（自愈后持续追踪更新效果）
- **UI 自愈 Agent 层**：知识库（业务知识/历史经验/弹窗特征库/规则模板）+ 智能引擎（弹窗分析/文本变更感知/元素变更感知/智能等待）+ 智能决策体（问题感知&智能诊断/行动智能决策，即"自愈大脑"）
- **基建&依赖**：驱动 = Android/iOS/Harmony/adb/tidevice/hdc/云真机；悟空平台 + PaddleOCR

#### 2.2 五步诊断法（失败后按顺序定位根因）
1. 设备健康检测（lsusb 远程连接、ping 网络、磁盘、内存）
2. 自动化框架状态检测（Appium 服务端口、驱动进程 ps、client-server 会话）
3. 页面弹窗分析（VLM 视觉语言大模型 + 弹窗知识库，识别弹窗类型和处理意见）
4. 页面同步分析（VLM 分析页面加载状态和内容完整性）
5. 页面感知分析（大模型融合控件画像 + 历史基线多模态数据比对，感知文本/元素变更）

→ 输出诊断（弹窗中断/元素变更/UI 未同步/平台异常/设备异常）→ 修复指令（原子动作 `Click(x,y)` + 被替换定位器 `original_find_type/value/index`；置信度 > 0.8 才采纳）

#### 2.3 服务调度（工程化关键）
- **并发调度**：并发拉起多类信号检测，同一诊断窗口内快速收敛
- **超时与降级**：单检测器失败/超时不拖垮主流程，引擎返回"已完成结果 + 可执行决策"
- **统一决策路由**：异构信号归一为标准 `decision`，按优先级输出，避免策略冲突
- 时序：`UiSelfHealingMainService` → `diagnoseAsync` → `par` 并行多信号 → `UiHealingRecordService` 存记录 → `decide(bundle)` 按优先级决策 → 返回 `UiSelfHealingResult(decision, reason, detail, recordId)`；超时兜底返回 `(NONE, UNKNOWN)`

#### 2.4 弹窗引擎（如何让大模型认识弹窗）
- **难点**：跨平台多品牌（苹果/华为/小米/OPPO/VIVO/荣耀定制）、弹窗类型多样（系统级权限/通知/隐私合规 + App 级引导/协议）、表象多样（按钮排列不一致、交互文本不统一）。同一个"位置权限"弹窗各厂商文案就有"仅使用时允许/使用 App 时允许/仅在使用中允许/使用应用时允许……"
- **特征建模**：视觉模型（视觉布局+语义关键词）→ 结构化弹窗知识库 → 大模型推理。VLM 提取主体+按钮 → 语义分类（权限请求/系统提醒/隐私合规/厂商定制）→ 分析决策（同意/忽略跳过关闭/授予/定制处理）
- **智能处理**：从"规则驱动"升级为"理解驱动"。输出结构含 `isPop`、`popType`、`closeInfo`（含 OCR 坐标还原）、`requiredAction`。对比枚举法：AI 能处理未见过的弹窗变体、鲁棒性强、维护成本低、具备动态学习能力。

#### 2.5 页面感知引擎（如何感知页面变化）
- **多模态基线 vs 当前快照对比**：步骤截图 + OCR 文本集 + DOM 控件树 + 控件画像
  - VLM（视觉大模型）→ 文案变更（移除/变更）
  - LLM（大语言模型）→ 元素变更（移除/变更）→ 匹配新控件
- **多模态数据基线形成**（阶段一）：监听测试过程采集成功的关键步骤 → adb/tidevice 截图 + OCR 文本 + Appium 控件 → 按脚本步骤 MD5 匹配 → 控件画像 → 形成基线。数据清洗：截图压缩、剪裁非关键区（状态栏/导航栏）、DOM 冗余节点清洗（focusable）
- **多维度匹配**：语义层面（语义相似度/功能等价）、位置层面（视觉边界+相邻节点匹配）、结构层面（DOM 树变化比对关键路径，识别层级重构）
- **智能修复**：综合评估（匹配度 + 推理置信度）→ 综合决策 → 输出定位器 → 智能修复。变更类型分：文案优化 / 元素重构 / 布局调整。定位器策略：文案优化&元素重构时大模型输出新定位器；布局重构时优先健壮性强的方式（**id → 文本 → 优选 xpath → 绝对路径兜底**）。**步骤级重试**：精准定向修复，保留业务数据状态，避免重复之前步骤。

#### 2.6 控件画像："数字身份证"（防止大模型误判的关键）
把控件描述成三个维度，让大模型"理解"而非"泛化匹配"：
- **who（认识控件）**：类名/id/class + 功能类型（语义角色）+ 文本 + 视觉特征 + 交互属性 →识别"这是一个橙色的确认按钮"而非"一个 id=btn_confirm 的元素"
- **what（理解意图）**：页面语义（场景）+ 交互上下文 → 理解"这是隐私政策协议底部的同意按钮"而非任意"同意"文本
- **where（抗布局微调）**：DOM 路径/深度/父容器/兄弟节点/子节点

**大模型智能不失控**（核心洞察）：
- **语义防火墙防跨场景泛化**：问题是大模型会把"确认"在登录页 vs 支付页泛化。画像嵌入业务上下文（"订单状态显示区""支付流程中的按钮"），使大模型仅在匹配上下文中激活识别。
  - 案例：截图里"专票(撮合)"变成"开票"。未引入画像时大模型判为"文案变更 modify"（错误泛化）；引入控件画像后结合原图判为"移除 removed"（正确）。
- **空间关系锚定抗布局微调**：把节点的"路径定位"转化为"业务逻辑验证"（如"登录页面中，点击橙色登录按钮，完成登录态"）。

### 3. AI 脚本生成（PART 03）—— 减少新增脚本人工成本

**目标**：减少新增脚本人工录制和调试成本，自动生成可用脚本。

#### 3.1 方案选型（两条路径对比）
- 方案一：UI 视觉图 + 需求文档驱动（解析 UI 图 → 提取交互逻辑 → 生成步骤）— **依赖视觉完整性，稳定性不确定**
- 方案二：需求文档 + AI 规划驱动（结构化解析需求 → AI 推理执行路径 → 输出标准化脚本）— **依赖需求完备性，稳定性高** ✅ 选此路

#### 3.2 脚本生成方案：AI 执行场景 → 脚本
从"手工用例 AI 执行"过程中沉淀脚本：
- **输入**：AI 执行 log（thought/action/prompt）+ 视觉结构（OCR/DOM）+ 运行上下文（taskId/scriptId/device）
- **语义理解**：从混杂执行记录抽取稳定语义（意图/对象/结果），自然语言与动作标签对齐到可计算事件（日志语义/路径提取/噪声抑制）
- **标准化**：原子化步骤（一步一动作）、步骤排序、动作标准化输出，收敛到有限动作集（Click/Swipe/Input/Assert/qamtRequest）+ 定位策略（OCR/image/Source）

#### 3.3 手工用例 AI 执行 Agent
- 形态：测试用例自然语言转换（"输入手机号，勾选隐私政策后，获取验证码再输入验证码登录"）
- 轨迹：测试场景 AI 自主规划（附规划说明）
- 步骤：AI 执行（`adb shell input tap 365 876`）
- 架构分应用层（视觉执行 Agent / 多平台适配 / 页面检测 / 用例评估 / 多 Agent 协同 / 巡检 Agent / 业务 Agent / 脚本辅助 Agent）+ AI 层（VLM / 规划定位断言 prompt / 图像定位 / RAG / MCP Server / 模型评优）

#### 3.4 固化 AI 执行轨迹（工程化核心思想，最值得借鉴）
把 AI 一次成功执行的轨迹**固化成确定性脚本**：
- 从"概率性"到"确定性"：AI 每次思考路径/定位/动作序列可能不同，导致结果忽好忽坏 → 固化后稳定
- 从"实时推理"到"极速执行"：无需大模型推理时间，大幅提效
- **节约成本**：若每条业务线每次回归都靠 AI 实时规划，会产生"难以承受的 Token 账单"
- 无缝对接 AI 自愈：脚本执行对接自愈 Agent
- 最终产物：**MTC DSL 自动化测试脚本**

#### 3.5 步骤降噪
AI 执行过程有噪音（误触 Mistouch / 无效 Tap / 规划错误 Planning Error）。输入（文本步骤/tap 坐标/截图/UI 地图）→ AI 降噪：意图识别（核心动作+核心控件+业务目标）、类降噪簇（纠错/纠偏/无效重试/聚焦+输入）、白名单（造数/断言/输入等正常操作）、降噪策略（语义识别+多模态意图校准）、非预期识别（弹窗/浮层/广告）。

#### 3.6 & 3.7 两种定位落地
- **视觉定位**：视觉模型识别 icon 边界 rect/center → 缓存原图 → 按 bound 裁剪 → 脚本截图匹配 → 生成 `Click().by(image).with(image_xxx, sift)`。执行时模板匹配 + SIFT 特征匹配 → 点击图像。
- **DOM 定位**：位置（矩阵/中心）+ DOM 结构（属性/位置）→ 源坐标换算（源坐标系/设备分辨率/比例映射）+ UIAutomator XML（标记空间相交节点/几何偏移折优/序号编码）→ 预期固定（唯一候选 `.by(id)`；多候选用 `.index(n)` 指定并加 `.intent` 注释）

### 4. 实践效果（PART 04）

#### 4.1 范式变更：人工驱动 → AI 驱动
- 传统人工线性模式：需求/用例 → 人工理解 → 人工录制/写脚本 → 人工调定位/补断言 → 平台执行 → 失败人工排查 → 人工修脚本 → 版本迭代后再次失效（死循环）
- **AI 闭环飞轮**（8 步）：① 功能用例 AI 生成 → ② 自然语言 AI 执行 → ③ AI 执行日志沉淀 → ④ AI 生成 UI 脚本 → ⑤ MTC 调度执行 → ⑥ 执行失败 AI 自愈 → ⑦ 脚本自动更新 → ⑧ 资产沉淀&反哺（回到 ①）
- 全链路价值：生产降本 / 执行提稳 / 维护减负 / 资产沉淀 / 持续进化

#### 4.2 生成&修复&持续效果评估（五步）
脚本生成&验证 → 执行时自愈诊断（弹窗/元素变更/网络超时）→ 修复并重试（智能处理弹窗、替换缓存重试）→ 记录结果&更新脚本 → 追踪执行成功率。
- 自愈实时性：异常发生在步骤执行当下即触发诊断，不等任务结束
- 数据闭环性：先运行时修复保障任务继续，再异步把有效修复固化到脚本
- 效果可度量：对每次脚本更新版本持续跟踪后续成功/失败

#### 4.3 更新安全机制（重要的工程治理）
- **通知机制（变更可见）**：自动更新成功后推送飞书卡片给 creator 和审核人，展示脚本信息、步骤序号、old→new 变更摘要、报告链接。让责任人第一时间知道"改了什么、影响哪里、是否可接受"。
- **回滚机制（风险可控）**：每次更新保存修改前后快照，支持按更新记录一键恢复；支持"不接受并回滚"，记录 Bad case 持续改进。
- 变更摘要示例：`# AI_SELF_HEALING=28648 LOCATOR_FIX by=id->id with=...btn_add->...btn_confirm_send`、`TEXT_FIX old=高速费 -> new=高速路桥费`

#### 4.5 收益数据（少见地给了量化）
- 脚本生成**首次通过率 90%+**
- 平均脚本通过率**从 80% 提升至 90%+**
- 脚本自愈成功数 **5000+**（高频脚本落地验证）
- 节省脚本维护人力 **60%**

## 对照本项目（autotest2py）的启发

> 货拉拉做的是移动端（Appium + adb + 自研 DSL），本项目是桌面 Electron（Playwright + `framework-v2`）。技术栈不同，但**方法论高度可迁移**。

### 直接可借鉴的点

1. **控件画像 / 语义防火墙 → 对标本项目 `ui-contracts`**
   本项目已有 `ui-contracts/`（selector 版本化 + UI 契约注册表），但目前是"静态契约"。货拉拉的"控件画像 who/what/where + 业务上下文嵌入"提供了升级方向：让 selector 不只是字符串，而是带语义角色和场景上下文的描述，抗文案/布局漂移。

2. **五步诊断法 → 对标本项目失败定位**
   本项目失败时目前靠 CDP explorer 人工排查。货拉拉的"设备健康 → 框架状态 → 弹窗 → 页面同步 → 页面感知"分层诊断，可作为 `framework-v2` 增加自动诊断层的蓝本（Electron 版可简化为：进程健康 → 页面 ready → 弹窗/Modal → DOM diff）。

3. **固化 AI 执行轨迹（3.4）→ 最值得借鉴的思想**
   "AI 实时规划成本高且不稳定 → 把成功轨迹固化成确定性脚本"。这正好回应了 `chatbox-pro` 同步方案里"live Agent 概率性 flaky、不当门禁"的顾虑——可以让 AI 探索式生成，跑通后固化成稳定 spec 进回归集，日常门禁用固化脚本，与本项目"稳定 case 收敛进正式回归"的思路一致。

4. **更新安全机制（4.3）→ 对标本项目 `sync-impact`**
   本项目已有 `sync-impact`（chatbox-pro 提交 → 映射回归改动 + 飞书/Slack 推送）。货拉拉的"变更可见（old→new 摘要卡片）+ 一键回滚 + Bad case 记录"可补齐本项目自愈/自动更新时的治理闭环。

5. **多模态基线 + 步骤 MD5 匹配 → 对标 RAG/视觉实验**
   本项目有 `rag-ab-eval`、`accessibility` 实验。货拉拉"截图+OCR+DOM+控件画像按步骤 MD5 形成基线"的数据组织方式，对本项目做视觉回归/AI 断言有参考价值。

### 差异与不适用的点

- 货拉拉重度依赖 OCR + 视觉定位（移动端无稳定 DOM 语义），本项目是 Electron/Chromium，有完整可访问性树和稳定 DOM，**应优先 DOM/TestID 定位，视觉仅兜底**（与货拉拉 `id → 文本 → xpath → 绝对路径` 优先级思路一致）。
- 货拉拉的"弹窗引擎"针对多品牌 Android 系统弹窗，本项目桌面端弹窗类型有限（应用内 Modal + 系统权限），不需要那么重的品牌适配层。
- 收益数据（90%+ 通过率、5000+ 自愈、省 60% 人力）是货拉拉 18000+ 存量脚本规模下的产物，本项目脚本规模小，投入产出比需重新评估——**不必照搬自愈基建，优先借鉴"固化轨迹 + 变更治理"轻量部分**。

### 一句话总结
货拉拉这套 = **AI 生成脚本（降生产成本）+ AI 自愈脚本（降维护成本）+ 固化轨迹（保稳定/控 Token）+ 变更治理（可见/可回滚）** 四件套组成的闭环飞轮。对本项目最有价值的不是它那套重型移动端自愈基建，而是**"固化 AI 执行轨迹"和"更新安全机制"这两个工程思想**。
