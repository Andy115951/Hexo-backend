# Test Case Step 1 Generic — 通用测试建模

**目标**：先系统性理解需求或代码变更，再暴露风险、边界和影响范围，最后形成可评审的测试建模文档。  
**边界**：本 skill **不写具体测试用例**，只输出 step1 建模结果。

---

## 1. 适用场景

当用户希望基于以下任一输入产出测试设计时，使用本 skill：

1. `PRD` / 需求文档 / 产品说明
2. `commit id`
3. `PR` 链接 / 变更说明
4. `diff`
5. 模块功能描述或接口设计说明

如果输入同时包含产品需求和代码变更，优先结合两者一起分析，不要只看其中一边。

---

## 2. 核心原则

### 2.1 先理解，再建模

不要一上来直接写测试点。  
先判断这次输入回答的是哪一类问题：

1. 这是一个新功能 / 需求设计问题
2. 这是一个代码变更 / 回归影响分析问题
3. 这是一个内部机制 / 升级 / 迁移 / 稳定性问题

### 2.2 输入源不同，分析重点不同

如果输入是 `PRD` / 需求文档：

1. 优先梳理业务目标、用户流程、业务规则、边界条件
2. 明确哪里是显式规则，哪里是隐含约束
3. 找出需求里没有说透，但测试必须补齐的问题

如果输入是 `commit / PR / diff`：

1. 优先理解改动点、前后差异、影响范围、上下游关联
2. 尽量还原“改之前是什么逻辑，改之后变成了什么逻辑”
3. 判断是否会影响已有功能、兼容性、异常路径或数据安全

### 2.3 不只看改动点本身

无论输入是 PRD 还是代码变更，都必须尽量覆盖：

1. 主功能
2. 相关功能
3. 上下游依赖
4. 边界值
5. 异常路径
6. 状态切换
7. 数据一致性
8. 权限 / 隔离 / 安全风险

### 2.4 输出要可承接 step2

step1 的输出必须足够结构化，便于后续直接转成表格化用例，而不是只给一段松散分析。

---

## 3. 文档类型先判定

一次 step1 默认只产出一种文档类型：

1. `功能 E2E`
2. `内部机制 / 升级回归`

判定规则：

1. 如果主要目标是验证用户流程、业务行为、功能结果，优先选 `功能 E2E`
2. 如果主要目标是验证迁移、存储、恢复、隔离、补偿、稳定性，优先选 `内部机制 / 升级回归`
3. 不要默认混写两种视角
4. 只有用户明确要求“两套都写”时，才拆成两份文档

输出文档开头必须显式写明：

```markdown
- 文档类型：功能 E2E
```

或

```markdown
- 文档类型：内部机制 / 升级回归
```

---

## 4. 输出路径与文件约定

### 4.1 输出路径优先级

1. 如果用户明确指定输出路径，使用用户指定路径
2. 如果用户未指定，默认输出到当前工作区下：

```bash
tests/test-case-docs/
```

### 4.2 文件命名建议

建议命名：

```text
{topic}-{mode}-step1.md
```

例如：

1. `order-refund-e2e-step1.md`
2. `session-storage-internal-step1.md`

---

## 5. step1 执行流程

按顺序完成以下步骤。

### 5.1 识别输入类型

先在文档开头补一段简要说明：

```markdown
## 输入来源

- 类型：PRD / commit / PR / diff / 模块说明
- 输入对象：{简述}
- 本次分析目标：{功能验证 / 回归影响 / 内部机制风险}
```

### 5.2 提取关键信息

如果输入是 PRD，提取：

1. 目标用户
2. 核心流程
3. 业务规则
4. 关键状态
5. 边界条件
6. 约束或依赖

如果输入是 commit / PR / diff，提取：

1. 改动模块
2. 核心逻辑变化
3. 改前 / 改后差异
4. 影响范围
5. 关联模块
6. 潜在回归点

### 5.3 先列“需求冲突 / 信息缺口”

如果输入本身不完整、规则冲突或上下文缺失，必须先列出来。

```markdown
## 需求冲突 / 信息缺口

| 类型 | 描述 | 影响范围 | 是否阻塞 |
|------|------|----------|----------|
| 缺失 / 冲突 / 待确认 | {描述} | {模块/流程} | 是/否 |
```

### 5.4 定义范围

```markdown
## 范围定义

In scope:
- {本次覆盖内容}

Out of scope:
- {本次明确不覆盖内容}
```

### 5.5 流程逻辑总览

按用户视角或触发链路拆解完整流程。

对于 `功能 E2E`：

1. 用户入口
2. 核心处理
3. 分支判断
4. 最终结果
5. 异常提示

对于 `内部机制 / 升级回归`：

1. 先写用户或系统触发点
2. 再写内部机制处理
3. 最后写用户可感知结果或数据结果

### 5.6 数据与状态建模

至少补齐：

1. 关键实体
2. 关键字段
3. 关键状态
4. 状态流转约束
5. 数据一致性要求

建议输出：

```markdown
## 数据模型与关键约束

| 实体 | 关键字段 | 约束 / 风险点 |
|------|----------|---------------|
| {实体} | {字段} | {说明} |
```

```markdown
## 状态与流转

| 状态 | 进入条件 | 退出条件 | 风险点 |
|------|----------|----------|--------|
| {状态} | {条件} | {条件} | {说明} |
```

### 5.7 风险与异常建模

至少覆盖：

1. 边界值
2. 非法输入
3. 空数据 / 脏数据
4. 超时 / 失败 / 重试
5. 并发 / 幂等
6. 权限 / 安全 / 隔离
7. 回滚 / 恢复 / 补偿
8. 兼容性 / 升级回归

### 5.8 测试矩阵

从规则中抽关键维度，不要机械穷举，但要明确高风险组合。

```markdown
## 测试矩阵

| 维度 | 取值 |
|------|------|
| 用户角色 | {取值} |
| 状态 | {取值} |
| 数据条件 | {取值} |
| 异常条件 | {取值} |
| 依赖条件 | {取值} |
```

```markdown
## 高风险组合

1. {组合1}
2. {组合2}
3. {组合3}
```

### 5.9 风险裁剪建议

最后给出后续 step2 的优先级建议：

```markdown
## 风险裁剪建议

- P0：{必须覆盖}
- P1：{建议覆盖}
- P2：{可选补充}
```

---

## 6. step1 输出结构

最终输出文档建议包含以下结构：

```markdown
# **{主题} 测试建模**

- 输入来源：{PRD / commit / PR / diff}
- 文档类型：功能 E2E / 内部机制 / 升级回归
- 分析目标：{说明}
- 版本日期：{yyyy-MM-dd}

## 需求冲突 / 信息缺口
## 范围定义
## 流程逻辑总览
## 数据模型与关键约束
## 状态与流转
## 风险与异常建模
## 测试矩阵
## 高风险组合
## 风险裁剪建议
```

---

## 7. 禁止行为

1. 禁止在 step1 直接写 Given/When/Then 用例表
2. 禁止只有“功能列表”，没有流程、状态、数据和异常分析
3. 禁止只围绕改动代码行本身分析，而不考虑关联功能和影响范围
4. 禁止把 `功能 E2E` 和 `内部机制 / 升级回归` 混写成一份模糊文档
5. 禁止只写显性 happy path，不写边界、失败和恢复路径

---

## 8. 完成标准

step1 完成时，必须满足：

1. 已明确输入来源与分析目标
2. 已明确文档类型
3. 已定义 in scope / out of scope
4. 已覆盖流程、数据、状态、异常、风险矩阵
5. 已给出 step2 可承接的风险裁剪建议

完成后，交由 `test-case-step2-generic` 继续生成结构化用例。
